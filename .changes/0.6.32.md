## 0.6.32 - 2026-09-22
### Added
* Added a commit-msg git hook that keeps local-tool configuration paths and AI-attribution mentions out of commit messages. The existing pre-commit hook scans staged content, but no hook ever received the message itself, so the message was the one unguarded surface; 13 messages on the public branches had picked up such a mention since 2026-05. It shares the pre-commit leak and exception patterns byte-for-byte, pinned by a test so the pair cannot drift, and adds a message-only pattern for the prose forms the content scan does not need to match. Vendor identifiers the AI connector depends on - protocol schemes, SDK package names, canonical env-var names, and the provider key itself - remain allowed. Fails open, and git commit --no-verify still bypasses it. Contributor clones pick the hook up through the core.hooksPath that post_install already installs.
* The maintenance status payload (`GET`/`POST /_gina/maintenance`, both engines) now carries `pid` and `hostname` — the process that answered, and under Kubernetes the pod name. The runtime override was always per process: it lives in the memory of the process that received the `POST` and — unless the replica sync below (`server.maintenance.store`) is configured — is neither written nor broadcast, and a replica that restarts returns to its configured state. That contract is now stated on the guide, the schema and `llms.txt`, and the two fields let an operator fanning a `POST` out over replicas read back which ones applied it; `enabled: true` in configuration remains the durable, deployment-wide form
* Maintenance mode can now be turned on from the environment: a bundle started with `GINA_MAINTENANCE=1` (or `true`) boots with its maintenance gate closed, exactly as if `settings.json > server.maintenance.enabled` were `true` — for replacement pods created during a window, or any process that must come up closed without a configuration edit. The variable can only close a bundle, never open one: `0`, `false` or an unset value leave the configured state in place, and any other value is ignored with a boot warning naming the accepted values. The runtime toggle keeps its meaning — `POST /_gina/maintenance {"enable":false}` still reopens the process — and `GET /_gina/maintenance` reports `source: "env"` for a closure that came from the variable. Honoured under both launchers (`gina bundle:start` and `gina-container`); under the daemon the variable must be present in the environment of the process that started the daemon (a pod init script), because a warm daemon passes only its launch-time environment to the bundles it spawns.
* Maintenance mode can now stay coherent across the replicas of one deployment. Point `server.maintenance.store` at a declared kv namespace (redis-backed for replicas on different hosts, sqlite-backed for processes on one host) and every `POST /_gina/maintenance` writes its runtime override there, while each process polls it (`pollInterval`, default 2000 ms, an unref-ed timer) — so one POST anywhere closes or reopens every replica within one interval, and a replica joining mid-window follows the shared state within one store round-trip. The gate itself keeps reading local memory synchronously. A store outage freezes each replica in its last-known state and never reopens a closed site; a `ttlSeconds` window expires deployment-wide through the record TTL; an `enable:false` is written, not deleted, so it wins over a configured `enabled: true` on every replica exactly as it does locally. A namespace the kv primitive cannot hand out, or one running `failMode: "open"`, refuses the boot with a message naming the fix; a memory-backed namespace runs with a boot warning that replicas will not follow each other. `GET /_gina/maintenance` gains a `sync` field (`store`, `key`, `lastSyncAt`, `lastError`) and a `POST` reply carries `store: {written, error}` — a write that fails still applies locally and answers 200 with `written: false`. Without `store` nothing changes.
* A form can swap its `text/html` XHR answer into any element of the page, htmx-style, with three attributes on the `<form>`: `data-gina-form-target` (the `hx-target` grammar - `this`, `closest <selector>`, `find <selector>`, or a CSS selector; `next`/`previous` reserved), `data-gina-form-swap` (`innerHTML` by default, `outerHTML`, `textContent`, `beforebegin`, `afterbegin`, `beforeend`, `afterend`, `delete`, `none`) and `data-gina-form-select` (a CSS selector picking the part of the answer to swap, every match). The target is resolved at submit, from the form, and a target or strategy that cannot be honoured refuses the submit before anything is sent (`error` callback with `{ status: 422, reason: 'targetError' }`). The success payload keeps `contentType`/`content`/`status` and adds `data`/`view` (the action's data when the answer carries the dev-mode hidden inputs, `null` otherwise), `target`, `swap` and `swapped`. Two events on the form for the main swap: `beforeswap` (cancelable with `preventDefault()`; `detail.content` may be rewritten) and `afterswap` (after the region is bound; declarative hook `data-gina-form-event-on-swap`). The swapped region is bound through the shared `bindRegion()` policy: src scripts the document does not have are re-created once, forms that opt in are bound, `data-gina-link` anchors too; a swap that replaces the submitting form binds its replacement after the `success` callback. A declared target wins over the popin the form is in; absent, a form inside a popin keeps loading its answer into that popin (https://github.com/gina-io/gina/issues/76)
* `lib.duration.parse()` — the framework's one parser for unit-suffixed duration strings (`"500ms"`, `"30s"`, `"15m"`, `"3h"`, `"15d"`; the unit is required, a bare number is refused with `NaN`, `"0s"` is legal). It is the parser `lib/storage` already used for its interval keys, promoted to a registry entry so every configuration key that names a span of time shares one dialect; storage delegates to it and its behaviour is unchanged.
* Per-bundle login session cookie lifetimes, declared in a bundle's `security.json`. `session.expires` sets the cookie lifetime applied at `req.login()` for an ordinary login and `session.remember` the lifetime for a login that asked to be remembered — both unit-suffixed duration strings (`"15m"`, `"3h"`, `"15d"`; the unit is required). A login counts as remembered when the caller passes `{ remember: true }` to `req.login()`, or when the login request carries a truthy `remember` field (`on`, `1`, `true`, `yes`); an explicit option always wins over the request field. Both keys are optional and a bundle that declares neither behaves exactly as before. These two keys were documented but interpreted by nothing until now, so a value already sitting in one may not be a duration string: such a value is reported at boot naming the bundle, environment and key, and then ignored — the bundle keeps the cookie lifetime it already had and the boot is never refused. Everything that governed a session before still does: an application setting `req.session.cookie.maxAge` in its own login callback still wins, an absolute session timeout still caps the total lifetime, and a session store's `ttl` still governs the server-side record independently of the cookie. Declared in the published `security.json` schema.
* A form's `text/html` answer can update elements anywhere in the page, independently of where the answer itself goes: any element of the answer carrying `data-gina-swap-oob` is swapped into the page element with the same `id` (htmx's `hx-swap-oob`). `true` or an empty value replaces that element (`outerHTML`); a strategy name (`innerHTML`, `textContent`, `beforebegin`, `afterbegin`, `beforeend`, `afterend`, `delete`, `none`) applies the out-of-band element's CONTENT, the wrapper being dropped; `<strategy>:<selector>` is reserved. Out-of-band elements are always removed from the answer, whether or not they swapped, so the main fragment stays clean, and they run BEFORE `data-gina-form-select` narrows it, so an element outside the selection still lands; where both address the same element, the main swap wins. They are processed on all three answer paths - a declared `data-gina-form-target`, a form rendered inside a popin, and a form with neither - so an answer carrying nothing else still updates the page. A missing `id`, no matching page element, a reserved or unknown value: the element is dropped and reported with a `reason`, never thrown, and named in a dev-mode console notice. The success payload gains `oob` (one entry per element: `id`, `strategy`, `swapped`, and `reason` when it did not swap) and `remainder` (the answer without them - what a handler should insert, since `content` stays the raw answer and would land them twice); both are absent when the answer carried no out-of-band element. Two events per element: `oobbeforeswap` (cancelable with `preventDefault()`; `detail.content` may be rewritten) and `oobafterswap`, each carrying `oob: true` and `oobId`. A form inside a popin updates the page behind it this way, and when nothing but out-of-band elements was addressed the dialog keeps its own content rather than being blanked. An out-of-band swap that replaces the submitting form rebinds it after the `success` callback, as a main swap does. An element wrapped in a `<template>` is honoured, and a wrapper emptied of them is dropped with them. An answer with no `data-gina-swap-oob` anywhere takes exactly the path it did before (https://github.com/gina-io/gina/issues/76)
* A server can now have the last word on where a form's `text/html` answer goes and how: three response headers, read at settle once the answer is known to be HTML and before `beforeswap`, override the form's declared `data-gina-form-target` / `-swap` / `-select` — `X-Gina-Retarget` (the target grammar: `this`, `closest <selector>`, `find <selector>`, a CSS selector; it creates a target where none was declared, replaces a declared one, and wins over the popin a form sits in), `X-Gina-Reswap` (one of the nine strategies) and `X-Gina-Reselect` (a selector applied to the answer) — htmx's `HX-Retarget`, `HX-Reswap` and `HX-Reselect`. The invalid-value rule is asymmetric: a Retarget that cannot be resolved means no swap at all, not into the declared target and not into the popin, and the success callback still runs with `swapped: false` and `reason: 'retargetError'` (never an error callback: the request succeeded); an invalid Reswap or Reselect is ignored and the declared value kept, as is either one without any target. Every refused or ignored value is named in a dev-mode console notice, and the success payload gains an `overrides` key — present only when the answer carried at least one of the headers — with one `{ value, applied, reason }` entry per header; `beforeswap` receives the same object in its detail and keeps the last word. A JSON answer never reaches the read. The three headers are honoured only from a response whose origin is the page's own - the transport's `responseURL`, the URL after redirects, against `location.origin` - so a responder elsewhere may neither choose the element its answer lands in nor reshape or trim the swap the form declared: a cross-origin Retarget is refused exactly as an unresolvable one (no swap, `reason: 'crossOrigin'`), a cross-origin Reswap or Reselect is ignored and the declared value kept, and a transport that cannot say where the answer came from (no `responseURL`, or an opaque origin on either side) reads as not-same-origin. `Access-Control-Expose-Headers` therefore changes nothing for these three. htmx needs no such read because `selfRequestsOnly` refuses the cross-origin request itself; a form here posts to its raw `action`, so the gate lives at the read (https://github.com/gina-io/gina/issues/76)
### Changed
* The popin context a request and its answer carry is decided by containment - the popin the submitting form is inside - instead of by whichever popin is open: (1) the `X-Gina-Popin-Id` / `X-Gina-Popin-Name` request headers, and therefore `self.isPopinContext()`, `Setup.isPopinContext` and a popin-style XHR redirect from `self.redirect()`, are now produced only for a form rendered inside a popin, not for a page form submitted while a popin happened to be open; (2) a plain `location` XHR redirect answering a page form navigates the page instead of being loaded into an open popin, and a name-less `location` redirect arriving after its popin was closed no longer reopens it; (3) `getActivePopin()` no longer returns a registered popin that is not open, so a no-argument `gina.popin.close()`, `destroy()` or `unbind()` during a popin's own click-time load window is a no-op, and with two popins open the most recently opened one is the active one rather than the first registered; (4) a name-less `popin: { close: true }` answer with nothing open to close is a no-op rather than a `422`. A page that deliberately fed a non-modal popin from a page form's answer sees the dev-mode notice and keeps that behaviour explicitly with `data-gina-form-target` pointing at the dialog, or by rendering the form inside the popin (https://github.com/gina-io/gina/issues/76)
* Fragment navigation (`gina/nav`) binds the swapped region through the same policy the validator now uses for form-answer swaps, the shared `bindRegion()` helper (utils/dom): the fragment's src-bearing scripts the document does not already have are re-created once, `data-gina-link` anchors are bound through the live link plugin, and forms are bound ONLY when they opt in (#B549: a `data-gina-form-*` attribute, an id naming a registered rule, or a `gina-upload-*` id). A bare id-bearing form inside a navigated fragment was bound regardless, and its submit silently became an XHR - the pre-#B549 bind-everything shape re-entering through swapped content (measured on the real bundle: bound and posted over XHR after a swap, left alone on the initial page). Such a form now keeps its native submit; add `data-gina-form-rule` or any `data-gina-form-*` attribute to opt it in. The validator publishes the gate as `gina.validator.bindRegion($root)` (https://github.com/gina-io/gina/issues/76)
* Two forms whose answers land in the same region no longer race. A form already declares, at submit time, where its answer goes and what it does when it gets there, and that is the whole of what the decision needs: when `data-gina-form-swap` REPLACES the region the form targets - `innerHTML` (the default), `outerHTML`, `textContent` or `delete` - a newer submit into the same target SUPERSEDES the request still in flight, whose answer was about to be overwritten anyway; when the swap ADDS to the region (`beforebegin`, `afterbegin`, `beforeend`, `afterend`) or writes nothing (`none`), there is no conflict to resolve and both land, exactly as before. Nothing is declared for any of this. The key is the RESOLVED swap target, which is what makes two DIFFERENT forms coordinate at all - a form-keyed guard never sees them - and a form declaring no `data-gina-form-target` is untouched, the module-wide `withRateLimit` rule still governing it and its own re-submits. BEHAVIOUR CHANGE, in exactly one shape: two or more forms targeting one element with a replacing swap, where both answers used to arrive and the older one is now aborted. Declare `data-gina-form-sync="queue"` on the later form to serialise them instead, or an insertion swap if what was wanted was both. `data-gina-form-sync` on the form overrides the derived decision where it is wrong - `replace`, `drop` or `queue` (one submit waits per region, the most recent) - and when declared it owns that form's decision, the module-wide `withRateLimit` option yielding to it so `replace` and `queue` are reachable without changing a global. Three htmx `hx-sync` spellings are REFUSED rather than parsed, each with a message naming the reason and the alternative: `abort` (its disposable-GET idiom, where a form submit is a validated POST with side effects - use `replace` or `drop`), the `queue first|last|all` modifiers (htmx has them because its trigger spec has `queue:` modifiers of its own; there is no trigger spec here, and one submit waiting per region is the only thing that region can act on), and `<selector>:<strategy>` (it names the element to coordinate on, which is already known - the resolved swap target). A superseded request releases everything it held - its trigger, its loading state, its a11y state - and then stops: it fires a new `abort` event on the form, `{ status: 0, reason: 'superseded', sync, derived }`, and never reaches the `error` channel, so the 408 an aborted transport would otherwise look like is not raised and `data-gina-form-event-on-submit-error` never sees it. Superseding cancels the client's WAIT, not the server's WORK: a superseded request was already in flight, so it may have reached the server, and if it did its writes stand - a page must never read `abort` / `superseded` as 'not saved' and resubmit, which would be a duplicate write. `derived` says whether the rule was read from the swap strategy or declared on the form, because the default needs no attribute and a page seeing the event may find nothing in its own markup that asked for it. The loading state follows the same logic: a submit turned away by `drop` releases the `data-gina-loading` its own click armed, since it will never reach a settle that could; a queued submit keeps it, being pending rather than abandoned. `data-gina-form-disabled-elt` holds elements disabled for the life of a request: a comma-separated list in the `data-gina-form-target` grammar, resolved before the request is opened and released at the one settle that covers success, error, abort and timeout alike. Each element is refcounted, so two overlapping requests naming the same element release it once, and marked `data-gina-disabled-by` with the form id; an element the page had already disabled is left alone and never cleared by us. An unreadable `sync` value or a part of `disabled-elt` that resolves to nothing refuses the submit before anything is sent - the same pre-send refusal a bad `data-gina-form-target` gets, `{ status: 422, reason: 'targetError' }` with `attribute` naming which one - deliberately louder than htmx, which skips an unmatched `hx-disabled-elt` silently (https://github.com/gina-io/gina/issues/76)
### Fixed
* The client validator boot scan now binds only the forms a page opted in - a data-gina-form-* attribute, an id naming a registered rule, or a virtual gina-upload-* id - and leaves any other form untouched, as the forms guide states. Before, declaring a single rule file made every form on every page an always-XHR submit, plain login and signup forms included, which expected a native POST (#B549). Behaviour change: a form that was bound implicitly now submits natively unless it carries a data-gina-form-* attribute or matches a rule; explicit validateFormById() and getFormById() calls are unchanged.
* Two connectors in one bundle no longer fight over an entity class name. The framework registers each entity's singleton in a process-wide table that was keyed on the bare class name, which is only unique within one model - so when two connectors of a bundle produced a class of the same name (guaranteed when they share a `database`, and equally possible across two databases that each carry a `user.js`), the one whose connection became ready SECOND was handed the first one's instance and never attached its own entities. Its `getModel()` returned a bare `{ _connection, getConnection }`, and because the bundle still started and served, every call on the missing entity failed later at request time. Which connector lost depended on connection timing, so it differed between replicas of the same release, and a dev boot could not reproduce it at all. The table is now keyed per bundle, model and class name. As a safety net, a bundle whose declared entity did not reach its model now names the class and refuses to start instead of serving a half-built model layer (#B555).
* A date field no longer submits the previous day for users east of UTC. `isDate` normalised the payload the way every validator does, but it wrote a `Date` OBJECT into it — and a `Date` is the one normalised type that does not round-trip through JSON: `JSON.stringify` renders it via `toISOString()`, which yields a UTC instant. Local midnight in any positive UTC offset is the previous day in UTC, so a user in Paris who picked `2026-09-18` submitted `2026-09-17T22:00:00.000Z`, and anything reading the date part of that string stored the 17th. It was silent because the instant was well-formed, and invisible to servers and CI running in UTC. The field now keeps the parsed `Date` — so `field.isDate(mask).format(...)` chaining is unchanged — while the submitted payload takes a plain `yyyy-mm-dd` string, always, whatever the input mask: the mask governs how input is PARSED, and gina already published these fields as `{type: "string", format: "date"}` in both its routing introspection and its DTO type emission, so the payload now matches the schema it was already advertising. BREAKING for anything that consumed the old shape: `req.body.<field>` is a string rather than a `Date`, and `new Date(payload)` on a date-only string resolves to UTC midnight rather than local midnight (#B558).
* `self.throwError()` now answers the request when it is called with a falsy value. The one-argument form passes the caller's own payload in the slot that the two- and three-argument forms use for the response, and the guard that protects it from running against an already-released response tested only that slot for truthiness. So `self.throwError(err)` where `err` was an empty string, `null`, `undefined`, `0` or `false` was mistaken for a call arriving after the response had gone: nothing was written, the request was never answered, and the only trace was a warning stating that the response had been released - which it had not - followed by no error text at all, because that message reads the status and message arguments and never the payload. Such a call now renders a 500 like any other. Genuine late calls, and calls made with no arguments, still bail exactly as before (#B560).
* An XHR redirect over HTTP/2 now delivers the session cookie it just rotated (#B550). `redirect()`'s XHR and popin exits answered through the raw HTTP/2 stream, which calls neither `res.writeHead` nor `res.end` — so a session middleware that sets its cookie from an `on-headers` hook and persists from an `end` proxy emitted neither, and a user signed in immediately before the redirect arrived unauthenticated, still presenting the session id that had just been replaced. Both exits now terminate through the compat response, as the sibling 303 exit always did. The router's one-shot `inheritedData` consume likewise persists itself instead of relying on that same save-on-end proxy, so a redirect that carried a credential-bearing body no longer leaves it in the stored session record for the rest of the session. HTTP/1.1 was never affected on either engine. The ordinary render path — a `rolling` cookie that did not roll, and session mutations dropped during a render — is addressed by #B562 in this same release.
* On HTTP/2, a `rolling` session cookie now rolls on an ordinary rendered response, and a session mutation made while rendering is persisted (#B562). The render delegates answer on the raw HTTP/2 stream, which calls neither `res.writeHead` nor `res.end`, so middleware that installs itself by wrapping those two methods — a session's `on-headers` cookie hook and its save-on-end proxy among them — was inert on every render: the cookie was never emitted, so a rolling expiry never rolled, and a mutation made during the render was silently dropped. A base `writeHead`/`write`/`end` is now installed on the response before the bundle middleware chain runs, so such middleware wraps it, and the six buffering render delegates hand their HTTP/2 send to that base `end` — which a session middleware invokes only once its store write has completed, so a response can no longer reach the client ahead of the record it depends on. The shim is transparent: a response that no delegate has claimed keeps its original methods, leaving redirects, statics and the built-in endpoints byte-identical. The framework-level error responder defers the same way, so an error answered over HTTP/2 now carries the session cookie it rotated and persists a mutation made while handling it. A base `_implicitHeader` is forced alongside the shim: an express plugin written against HTTP/1 calls it and `Http2ServerResponse` does not implement it, and while the router already forced it on the routed path, the middleware chain also terminates in the statics handler, so a statics-terminated request could otherwise reach a middleware-wrapped `end()` without it. The statics send sites stay on the raw stream deliberately: a static response runs no application code, so it has no session mutation to persist, and the one remaining difference is that a rolling session cookie does not have its idle timer refreshed by a static served over HTTP/2, where HTTP/1.1 does refresh it. `renderStream()` is deliberately unchanged — it writes chunk by chunk from an async iterable, and buffering it would alter SSE and Range responses. HTTP/1.1 was never affected on either engine.
* Fixed the storage metadata store running an application callback from inside its own try/catch. Seven methods - set, remove, acquireRef, releaseRef, listZeroRefs, removeIfZero and listKeys - invoked the callback inside the try that guards their SQLite statement, so an error thrown by the application was swallowed by the store, and the catch then invoked that same callback a second time with the application error presented as a store error. A caller that latches on first settle, as the content-addressed driver verify() does, treated the re-entry as a no-op and never completed, so the operation hung indefinitely instead of reporting. Callbacks now run after the try on every path, a genuine store error still arrives as fn(err), and get() already had the correct shape and is unchanged. (#B565)
* An HTML file served from a bundle's public directory over a dev boot no longer answers 500 when that bundle has no templates configuration (#B567). In dev the static handler injects the gina loader into an HTML static and read the bundle's `content.templates._common` block to do so; a bundle that never ran `view:add` — any API-only bundle — has no such block, so the read threw and the request answered 500 with a `TypeError`. The loader is now injected only when the bundle carries one; otherwise the page is served exactly as it is on disk, which is also what production always did. Pickup: a bundle restart; no rebuild.
* A JSON config carrying a `/**` docblock and, in a string value, a `/*` with no `*/` after it — a glob or certificate path such as `"…/ssl/*.example.pem"` — no longer hangs the bundle boot. The block-comment strip in `requireJSON` was a regular expression that backtracked about 2× per line (4× per CRLF line) following such a value, so a config with a glob path a few dozen lines from its bottom hung until the CLI start-wait killed the process, with nothing logged. The strip is now a linear, string-aware scan; a `/*` inside a quoted value is data and survives intact, where the regex also removed `/**/` out of glob values such as `"./lib/**/*"`. Everything else is unchanged: block comments are still stripped only when the file carries a docblock (#B568)
* A `preOpen: true` popin opened through the declarative `data-gina-dialog` trigger with the default (modeless) modal resolution now reaches `isOpen = true`. The loading shell is born modal, which sets the dialog element's `open` attribute to the empty string; `popinOpen` guarded its own open call with `getAttribute('open')`, which reads that empty string as absent, so on the modeless path it called `show()` on an already-modal dialog, the engine threw `InvalidStateError`, and the popin stayed visibly open while the framework recorded it closed - `close()` returned early, `getActivePopin()` ignored it, and a form inside it was routed as outside any popin. The guard now uses `hasAttribute('open')`, so both open calls are skipped for a shell-opened dialog; a modeless-declared popin that was pre-opened keeps the shell's modal presentation, as it did before (#B574)
* A form or link whose `text/html` answer is loaded into a popin now gets its DECLARED callback: `data-gina-form-event-on-submit-success` and `data-gina-link-event-on-success` are bound to the `.hform` / `.hlink` companion channels, and the popin branch of both XHR handlers returned after the bare `success.<id>` event, so a form inside a popin never saw its declared success callback run (only a programmatic `success.<id>` listener did). The companion now fires there too, with the parsed xhr-data as its payload, and `$form.eventData.success` is set as on every other path (#B571)
* A form's `text/html` XHR answer is now routed by the popin the SUBMITTING form is rendered in, resolved by containment at submit, never by "the active popin". A page form whose answer arrived while a popin was open had that popin's content replaced by the answer; arriving while a popin was still loading (reachable through a trigger opted out of preload, a programmatic load, or a click before the hover warm - not through a hovered default trigger) it raised a false `422` error callback, `Popin x is not open !`, after a successful server write; and with two popins open the answer landed in whichever open one had been registered first. The answer of a form that is not inside a popin is delivered to its own handler unchanged; a form inside a popin still loads its answer into that popin, and `popinLoadContent` now loads into the popin it is called on. `getActivePopin()` returns open popins only. In dev mode a console notice names the popin the former rule would have targeted (https://github.com/gina-io/gina/issues/76)
* A form or link whose `text/html` answer is loaded into a popin no longer raises a false `422` outside dev mode. The two hidden inputs the popin branch parsed (`gina-without-layout-xhr-data` / `-view`) are spliced by the server only when `NODE_ENV_IS_DEV` is true, so on any other boot the branch dereferenced an absent element, the error callback ran with a `TypeError` message after a successful server write, and the popin was never loaded. Both branches now go through one tolerant parse: the popin loads, the callback receives the parsed data in dev mode and an object carrying `status` otherwise (#B575)
* An `<name>.<env>.json` configuration overlay now wins on every key it declares. It was previously folded in before its base file and lost to it on any key both declared, so an environment-only key was added but an actual override was silently dropped — the opposite of what the reference pages have always described. Two consequences are observable and worth checking before upgrading: an overlay array now REPLACES the base array instead of being unioned into it, and a `null` in the overlay overrides the base value. Bundles with no overlay file are unaffected. This is the per-bundle configuration loader only; the `settings.*` template path is a separate mechanism and is unchanged.
* A `text/html` form answer whose top-level elements are table rows or cells no longer loses them. The answer was parsed as a whole document, so the HTML parser moved a top-level `<tr>` or `<td>` out of existence and a swap into a `<tbody>` wrote the cell text instead of the row, while a `data-gina-form-select` on `tr` matched nothing. The answer is now parsed as a fragment, so any element survives at the top level; a full-page answer drops its `<head>` rather than placing its `<title>` in the swap. Behaviour is byte-identical for answers that were already parsed correctly (#B578)
* A popin constructed with `preOpen: true` now treats the time between its loading shell showing and its content landing as an explicit state, `isLoading`, instead of a half-state nothing could name. Five things went wrong in that window: `loadContent()` on the popin threw `is not open !` for the whole round trip; `close()` returned without closing, so the shell could not be dismissed programmatically; a load that failed fired `error` and left the skeleton showing with nothing to dismiss it; a native Escape closed the dialog behind the plugin's back, and the content landing afterwards ran the real open and re-opened the dialog the user had just dismissed (measured on the published bundle); and the close-time teardown keyed on a class a dialog shell never carries. Now `loadContent()` on a loading popin injects into the dialog and completes the open, so `open` fires once, from that completion, and content still in flight lands afterwards as any later `loadContent()` would; `close()` and `destroy()` on a loading popin cancel the load (a transport still in flight is aborted, and a cancelled load fires no `error`), tear the shell down, release the trigger and fire `close`, so a dismissed dialog never comes back when its content arrives; the native `close` listener is bound when the shell shows, so an Escape during the load takes that same path; and a load that fails fires `error` first, so a listener that calls `loadContent()` keeps the dialog with its own content, then closes the shell if nothing handled it. A popin without `preOpen` shows nothing while it loads and never enters the state. Three visible changes: `loadContent()` no longer throws while the popin is loading, a loading popin closes, and a failed load closes its shell unless an `error` listener loaded content into it. `getActivePopin()` still returns open popins only, so a loading popin is not the active one (https://github.com/gina-io/gina/issues/76)
* Loading new content into a popin that is already open — `gina.popin.load(name, url)` on an open `data-gina-dialog` popin — no longer leaves the dialog empty. The landing wrote the new body and then fired the popin's `loaded` event with the popin object as its detail, the form of that event the legacy trigger's listener only binds on; the declarative trigger's listener applied the detail as if it were the body, and a body that is not a string is applied as nothing, so the content just written was wiped a moment later, with no error anywhere. That listener now applies nothing for a non-string detail, and the body written by the reload stays. Legacy `data-gina-popin-*` triggers were never affected. Present in every published version since 0.4.6, which introduced the declarative AJAX path (#B579)
* A malformed `data-gina-dialog-target` value no longer throws: `applyContent` guards the one read the selector engine can refuse, so a selector such as `#slot >` takes the documented fallback (a full replace of the dialog) instead of an uncaught `SyntaxError` inside the loaded-content and preload-consume handlers, which left the popin without its content and the open never fired (#B580). The partial swap's two silent fallbacks are now announced in dev mode, one `console.warn` per event naming the popin, the selector and which fallback ran: a selector matching nothing in the OPEN DIALOG falls back to a full replace (as documented), and a selector matching nothing in the ANSWER writes the whole answer body into the slot - the second fallback existed before but was undocumented. Production output is unchanged: the notices are gated on `gina.config.envIsDev`, and every fallback keeps the behaviour it had. The attribute keeps its plain-selector grammar on purpose: one selector runs on BOTH sides of the swap - it locates the slot in the dialog and the region in the answer - which makes it the dialog-scoped sibling of `data-gina-form-select`, not of `data-gina-form-target`; there is nothing to resolve relative to an element, so the `this` / `closest` / `find` grammar does not apply to it, and the four keywords are valid CSS that would silently match nothing anyway. Restart and re-bake (the browser bundle changed).
* A page form's staged upload is now placed with its own form. Which popin, if any, a chosen file belongs to is decided by containment - the popin the real form is inside, captured once at selection - never by "some popin is open" (#B572). Before, a file input in a page form whose file was chosen while an unrelated popin was open - through the file-picker race (a popin opening while the OS picker is already up) or a script assigning `input.files` - had its virtual `gina-upload-*` form appended inside that popin: the staging POST succeeded, none of the generated hidden metadata fields reached the form, the form then saved without the file, and the staging request carried that popin's `X-Gina-Popin-Id`. Nothing reported it. A form rendered inside a popin keeps the popin placement it always had. In dev mode the console now names the popin the former rule would have used. Restart and re-bake (the browser bundle changed).
### Security
* The built-in error pages now HTML-escape every value they render. A crafted link to any route whose action redirects - carrying a query string such as `?error=<script>...` - made the fallback error page reflect that value as markup and execute it in your application's origin, in every scope and on every released version; a newly scaffolded bundle, which configures no `errorFiles`, hit exactly that page. The same escaping is applied to the engine-level error page (whose text is built from the request path by its 404, 403 and 500 callers) and to the three nunjucks error-document fallbacks. Behaviour change: an application that deliberately passed HTML in an error title or message now sees it escaped - that reflection was the vulnerability. The scope gate on stack traces is unchanged (#B554).
* `self.redirect()` no longer lets a request parameter decide whether the redirect happens. A key named `error` in the incoming query string or request body was read as an instruction to raise an error, so any unauthenticated request to any route whose action redirects could force a 500 by adding `?error=` - on both engines, with no route opt-in, and in every released version. An EMPTY value was worse: the empty string is falsy, so the late-call guard inside `throwError()` mistook it for a call on an already-released response, logged "ignoring late error:" with nothing after the colon and returned without writing anything, leaving the request unanswered for as long as the client held the connection - and nothing reaps that, because `server.timeout` defaults to 0 so that SSE and WebSocket responses are not cut off. The key is now an ordinary parameter: it rides the redirect in `inheritedData` like every other one, which is what the documented "carrying request data across the redirect" example always described - that example could not work as written while the gate stood (#B559).
* Credentials no longer ride a redirect. `self.redirect()` carries the request's parameters to the redirect target - on the session as `inheritedData`, or in the target URL when the bundle has no session - and for a `POST` that container is the parsed body verbatim, so a login form's plaintext password was carried with it. On the session that meant the password was written to the session store, where on an authenticated flow it survived the redirect target's own request; where the bundle has no session it meant the password appeared in the redirect URL, and so in access logs, proxy logs, browser history and any `Referer` the target sends onward. A rejected login attempt was carried the same way. Fields whose names match the framework's existing redaction list - the same maintained, tokenising matcher the Inspector uses to mask these values in its own pane, covering `password`, `secret`, `token`, `apikey`, `authorization`, `credentials` and their case and separator variants - are now dropped from what is carried, while everything else travels exactly as before; keys describing rules or configuration, such as `passwordRules`, are deliberately still carried. Behaviour change: an application that deliberately carried a field with one of those names across a redirect no longer receives it at the target and should pass it by another route (#B551).
* Over HTTP/2, a static file served by the built-in engine no longer carries another request's response headers (#B566). The first static request after boot registered a byte-serving listener on the server that kept that request's response object for the life of the process and served every later static through it, folding the captured response's headers — its `Set-Cookie`, its request id and its CORS headers among them — onto every other client's stream. Any middleware that sets a per-request header eagerly (the framework's own CSRF plugin does) turned that into a cross-user cookie delivery. The same listener served an HTML static it had not seen before as a raw binary, and once a directory URL had been requested it answered that directory's index URL with a destroyed stream for the rest of the process's life. The listener and its server-push branch are removed: every HTTP/2 static is now served by the static handler on the request's own response, so it carries that request's headers, the dev `cache-control: no-store` set and the production `ETag`/`Last-Modified` with `304` support that the listener path never emitted. HTTP/2 server push, which browsers no longer support and which only a push-capable client could reach, is no longer implemented. Every published version is affected. HTTP/1.1 was never affected. Pickup: a bundle restart; no rebuild.
