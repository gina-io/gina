## 0.6.33 - 2026-09-25
### Added
* `server.query.http2SessionPool` (settings.json; an integer from 1 to 50, default 1): how many HTTP/2 client sessions `self.query()` keeps per upstream authority. The default keeps one multiplexed session per `hostname:port`, as before. A pool of N opens N sessions, filled round-robin call by call, so a per-connection (L4) balancer — a Kubernetes Service with no HTTP-aware ingress — spreads the calls over N upstream connections instead of pinning every call to the one pod behind the first connection. Any other value refuses the boot; the value is resolved once at engine start, so a change needs a bundle restart. Pickup: bundle restart, no re-bake (#P43)
### Changed
* The Isaac HTTP/2 rapid-reset guard (CVE-2023-44487) now counts the streams a CLIENT cuts short — a `RST_STREAM` of any code, or the peer destroying the stream, before the response completed — per session per rolling second, instead of counting new streams. Counting new streams made a sibling bundle's own multiplexed `self.query()` calls trip it: above 200 calls per second on one cached session the target sent `GOAWAY(ENHANCE_YOUR_CALM)` and every in-flight call failed with a 500 (17% of calls at 50 concurrent callers with default settings). A well-behaved multiplexing caller never resets a stream, so it never trips the re-scoped guard; new streams stay bounded by `maxConcurrentStreams`. The setting is renamed to say what it counts: `http2Options.maxStreamResetsPerSecond` (default 200). The old key `maxStreamsPerSecond` is no longer read — a bundle still setting it gets one boot warning and the default — because a raised value left over from the workaround must not quietly widen the reset limit. Two new pass-through keys, `http2Options.streamResetBurst` and `streamResetRate` (both required together), tune the runtime's own frame-level reset limit, which stays the primary guard: nghttp2 closes a session with `GOAWAY(INTERNAL_ERROR)` after a 1,000-reset burst (then 33/s), silently on the server side; gina's guard is the observable, configurable, tighter-burst layer on top. Not a vulnerability fix — the protection was in place; its scope changes so it no longer fires on the framework's own traffic. Engine-side aborts (a server-side destroy, the teardown a GOAWAY causes) are told apart and never counted. On Bun the runtime has no reset limit of its own and ignores both pass-through keys (one boot warning says so), so gina's guard is the only rapid-reset layer there; it reads Bun's own stream state to recognise a client reset, every reset code included. Pickup: bundle restart, no re-bake (#B611)
* `gina scope:add` now checks the whole scope name and refuses one it cannot use: a name is made of letters, digits, `_`, `.` and `-`, starts with a lowercase letter, a digit, `_` or `.`, and is neither `.`, `..` nor the name of a property every object inherits, such as `constructor`. It used to check the first character only. The `<bundle>/<scope>` form the command help documented as adding a scope to one bundle is retired: it never limited a scope to a bundle, it registered a project scope literally named `<bundle>/<scope>`. That form is now refused with a pointer to the per-bundle mechanism, the `scopes` allow-list on a bundle entry in `manifest.json`. A name that failed the old first-character check, such as `Staging`, used to be dropped without a message; it is now refused. Scopes already registered are unchanged, `scope:remove` still removes them, and the Couchbase connector still accepts a `/` in a scope, so a scope registered under the old form keeps booting. (#B626)
* `gina env:add` now checks the whole environment name and refuses one it cannot use, as `scope:add` now does for scopes: a name is made of letters, digits, `_`, `.` and `-`, starts with a lowercase letter, a digit, `_` or `.`, and is none of `.`, `..` and `global`, which already names the configuration overlay that applies to every environment. It used to check the first character only. The `<bundle>/<env>` form the command help documented as adding an environment to one bundle is retired: it never limited an environment to a bundle, it registered a project environment literally named `<bundle>/<env>`. A name that failed the old check, such as `Staging`, used to be dropped without a message; it is now refused. Both `env:add` and `scope:add` also refuse the name of a property every object inherits, such as `constructor` or `__proto__`: the project files are indexed by these names, and such a name would reach the shared prototype instead of an entry of its own. Environments and scopes already registered are unchanged. (#B639)
### Fixed
* The published package no longer carries Playwright `test-results/` artifacts. The directory is gitignored but `.npmignore` never listed it, so two `error-context.md` snapshots from a local end-to-end run shipped inside `gina@0.6.32` and `gina@0.6.33-alpha.1` — test fixtures only, with no credentials and no local paths (measured before this entry was written). `test-results/` and `playwright-report/` are now excluded from the tarball (#B581)
* With the Couchbase session store, logging in no longer answers 500 when the visitor's pre-login session was never saved (for example with `saveUninitialized: false`). Logging in rotates the session, which first deletes the old one, and the store reported deleting a session that is not in the bucket as an error, so the login failed through `req.login()` and through Passport 0.6 or later. Deleting an absent session is now a successful delete, as it already was on every other session store gina ships; any other error, such as a timeout, still fails (#B577)
* A `${secret:...}` reference whose key breaks the placeholder grammar `^[A-Z_][A-Z0-9_]*$` — lowercase or dotted (`${secret:db_password}`), empty, or a valid token padded with surrounding whitespace — is now REFUSED at config load, exactly like a missing key: the error names the config path and the grammar, never the offending text (the internal logger names it at debug level only). Previously such a value was passed through unchanged, so the literal placeholder text reached its consumer as a credential and the only symptom was that consumer's own failure much later, such as a database driver reporting an authentication error. Genuine mixed content (`https://${secret:HOST}/v1`) still passes through. `gina secrets:check` reports each malformed reference with its file, path and text and exits non-zero; `gina secrets:scan` lists them under "Malformed references"; `connector:test`, `connector:infer` and `connector:models` name the path instead of `<unknown>`. `lib.secrets` gains `getMalformedReferences(config)` beside `getRequiredKeys` and exports `MALFORMED_RE` beside `SECRET_RE`. A bundle that boots today with such a literal will refuse to start after upgrading — run `secrets:check` before the restart; it names every offending entry (#B583)
* A synchronous throw from a bundle's `onInitialize` callback — or the rejection of a promise an `async` callback returns — before it has emitted `'complete'` now aborts the boot with `[ FRAMEWORK ] onInitialize threw before emitting 'complete' — aborting boot: <reason>` on stderr and exit code 1, the same way a model-load failure does, so `gina bundle:start` reports the failure straight away and a container exits 1 with the reason in its log. Previously the throw was only logged: the boot stopped with nothing listening and no failure reported — `gina bundle:start` waited out its startup timeout and printed only "Check your logs", and under `gina-container` the process could even exit with code 0. A throw after `'complete'` still lets the bundle keep starting, and is now logged as such (#B576)
* A GET or HEAD query value whose text holds a percent-escape (`%0A`, `%22`, `%5C`, `%25`) is no longer decoded a second time: it used to turn the serialized query document into invalid JSON, so `req.get` came back EMPTY for the whole request (and a `validator::` requirement copying that data 404ed the route), while `100%2525` silently became `100%`. The data helper never percent-decodes a `{`-leading document any more; the isaac query parser decodes query KEYS once, like values (an HTML-form GET `user%5Bname%5D` still nests, and a `+` in a key is now a space, as express's query parsers, `qs` and `querystring`, already treat it). The same document path serves the browser validator, so a form value holding `%22`/`%0A` no longer empties the validated data set and a pasted `a%20b` is sent as typed; and it serves every route declaring a DTO, whose validated payload went through the same decode — an `application/json` body value holding `%20` reached the action as a space, and one holding `%22` left the action with no payload at all (`req.post` undefined); both now arrive as sent. Pickup: restart AND re-bake. (#B589)
* The published TypeScript declarations of two data-helper globals now match what the runtime does. `nestBracketNotationKey` takes the bracket path as an ARRAY (`['item', '0', 'id']`), which is what it has always required — a string nested character by character — so a TypeScript caller passing a string now gets a compile error instead of a silently wrong object; and `formatDataFromString` returns `object | undefined`, since a `{`- or `[`-leading input that does not parse as JSON yields `undefined`. (#B588)
* An `is` comparison between values that contain no ASCII letter or digit (`!!!`, `é€`) is now evaluated: it always failed, so a confirmation made only of symbols or non-ASCII letters could never pass. Pickup: restart AND re-bake. (#B602)
* A value containing a double quote, a backslash or a line break in a field that an `is` condition references (`$password === $passwordConfirm`) no longer stops the validation pass: the rule set was built by pasting the value in unescaped, so in the browser the form could not be submitted and on the server the validation threw. Such values are now compared exactly as typed, and `$&`, `$'` or `$$` in them are no longer rewritten (`ab$$cd` matched `ab$cd`). A referenced field with a number rule is compared as a number when its value is one and as text otherwise; a string literal written in a condition follows JSON escaping (one that is not valid JSON is read as written, as before); and a `$fieldName` value sent by a `query` rule reaches the endpoint as typed. Pickup: restart AND re-bake. (#B600)
* An `is` comparison no longer ignores parentheses and the word `return` inside the compared values: two values differing only by those characters (`ab(cd` and `ab)cd`, `myreturnpass` and `mypass`) compared as equal, in the browser, on the server and in route `validator::` requirements. Parentheses written around a condition's operands are still accepted. Pickup: restart AND re-bake. (#B601)
* A referenced value that itself contains a `$` followed by another field's name (`abc$email` in a password whose confirmation is checked with `$password === $passwordConfirm`) is no longer substituted a second time: the rule set was resolved one field at a time, re-reading the whole text after each splice, and the two-argument `is` form re-read the resolved condition once more — so such a value could never be confirmed, and, worse, two different values could compare equal (`abc$zeta x` confirmed `abcZ x` when a sibling field `zeta` held `Z`). Every `$` token is now resolved in one pass and the value is compared exactly as typed. Pickup: restart AND re-bake. (#B603)
* In a route `validator::` requirement or a fluent `is()` call, a `$field` token followed by a parenthesis or an operator — `($password) === ($passwordConfirm)`, `$a===$b` — now resolves; it used to resolve only when whitespace or the end of the condition followed it, so the condition was refused and the field read invalid. A field name holding a bracket or another RegExp character (`$pw[0]`, `$a+b`) resolves too. The rule is now the same on every path: the longest field name wins, a token ends at the first character outside `A-Z a-z 0-9 _ -`, and a `$` naming no field stays literal. (#B604)
* A `$fieldName` token in a `query` rule's `data` now names the right field whatever its spelling: `$passwordConfirm` was resolved as `$password` followed by `Confirm` (another field's value reached the endpoint), `$Email` was left as is, `$password` and `$password-confirm` in one body resolved by their order, a space after a token swallowed the text that followed it, and a `$` naming no field was sent as the string `null` — and threw while live-checking. Such a `$` now stays as typed. (#B606)
* Every request no longer re-reads the framework's environment template from disk. `Config` is constructed three times per request (route resolution, view detection and bundle-configuration lookup) and each construction parsed `core/template/conf/env.json` twice through `requireJSON`, which has no cache — six synchronous file reads and parses per request in every bundle, measured at 27% of a trivial JSON route's CPU (twelve per bundle-to-bundle call). The template is now parsed once per process, on the first construction, and shared read-only by every instance; nothing observable changes except the cost. Pickup is a bundle restart (#B610)
* The `/_gina/info` HTTP/2 `rstCount` metric had read 0 since it shipped: the server listened for a `rstCode` event on every stream, and `rstCode` is a stream property, not an event. It now counts the streams the client cut short before the response completed — the signal the rapid-reset guard counts (#B614)
* `self.query()` over HTTP/2: the client sent an `RST_STREAM(NO_ERROR)` after EVERY completed response — the settled-stream release ran `req.close()` while the stream was not yet marked closed — and the target's nghttp2 counted those frames against its CVE-2023-44487 reset rate limit, closing the cached session with `GOAWAY(INTERNAL_ERROR)` after about 1,000 calls (the `Session closed with error code 2` failures on long-lived bundle-to-bundle sessions). The release no longer closes the stream: a settled stream closes itself within milliseconds, and the listener drop alone releases it (#B613). An in-flight safe-method call cut by a server GOAWAY — `ERR_HTTP2_SESSION_ERROR` — is now retried on a fresh session under the same safe-method / `retryUnsafe` rule as a stream error; a non-safe method is still never replayed. A session gone between the cache read and the send made `client.request()` throw synchronously (`ERR_HTTP2_INVALID_SESSION`), unguarded; it is now caught and retried on a fresh session for any method, since nothing was sent, and exhausts into a typed 503 (#B612). Pickup: bundle restart, no re-bake
* The in-memory Collection's `find()` and nested-path filters now compare string values with the `==`, `>` and `<` operators instead of throwing, and no longer break when a value or the filter contains a double quote or a backslash. Previously a single row whose string value held a double quote threw and failed the whole query; `==`, `>` and `<` were not recognised on strings (only `>=`, `<=`, `===` and `!==` were); and a space after the operator (such as `>= b`) was kept inside the operand and skewed the comparison. Both operands are now encoded before comparison; numeric and datetime comparisons are unchanged (#B609)
* The Isaac server never closed an idle HTTP/2 session: its 120 s idle timer closed only when `session.activeStreams` read 0, and that property does not exist, so the timer re-armed forever and idle sessions were left to the client or the network. An idle session is now closed gracefully after `http2Options.sessionIdleTimeout` (`"120s"`, `120000`; default 120 s, the value the timer always had): open streams finish, no new stream is accepted on that connection, and a client's next request opens a fresh one — gina's own client evicts the closed session and reconnects. `0` disables the close; a value that is negative, not a timeout, or above 2147483647 ms logs one warning and uses the default. A quiet open stream (an SSE stream between events) does not keep the session alive — the stream itself finishes — while a stream still sending data does. Node.js only: on Bun the key is ignored with one boot warning and idle sessions are not closed by the server (Bun 1.2 / 1.3 time out busy sessions, and a client's next request hangs after the close). Pickup: bundle restart, no re-bake (#B619)
* `self.query()` over HTTP/2: every eviction of a cached client session deleted the cache entry by KEY, so a dead session's late `close`, `error` or `goaway` — or an earlier attempt's retry branch — evicted the LIVE replacement a retry had just cached under the same key. The replacement kept running, keepalive ticking, in no cache: 148 + 160 upstream connections were still open 186 s after a load run (the bundle-to-bundle audit, 2026-09-24), and the next call opened yet another. Every eviction is now identity-checked — it removes only the session it belongs to — and the cache owns the "lost its slot" teardown: an entry that is replaced, LRU-evicted, capped out or deleted stops its keepalive and closes its session gracefully (in-flight calls finish, nothing new is sent on it) instead of leaking it. The per-process session cap now drains the oldest session the same way instead of destroying it under an in-flight call. Pickup: bundle restart, no re-bake (#B625)
* `self.query()` over HTTP/2: the pre-flight PING stormed. A cached session counted as stale 3 s after its last PONG while the keepalive pinged only every 5 s, so about 40% of the time every concurrent caller sent its own pre-flight PING; node cancels every ping past its outstanding limit of 10 with `ERR_HTTP2_PING_CANCEL`, and that cancel was read as a dead session — 22 healthy sessions evicted and reconnected per 10 s run at 50 concurrent callers (the bundle-to-bundle audit). Now one pre-flight PING per session serves every caller waiting on it, every response re-stamps the session as fresh (a busy session never pre-flights), and a cancelled PING is inconclusive: the call goes out on the same session and the keepalive skips that tick. Pickup: bundle restart, no re-bake (#B627)
* The boot warmup of HTTP/2 sessions (`server.warmup`) never kept a session on Node.js: its initial PING was sent while the session was still connecting, node cancels such a ping at once, and the warmup read the cancel as a dead session and tore it down within a tick — so the first real `self.query()` still met a cold connection. The PING is now sent once the session is connected, the warmed session is stamped fresh after its PONG (the first call does not pre-flight it), and it is cached with the same identity-checked eviction and graceful cleanup as a session `self.query()` opens itself. Pickup: bundle restart, no re-bake (#B629)
* `self.query()` over HTTP/2: a request refused before the upstream processed it is now retried for any method. The runtime refuses a request queued onto a session that has just started closing — the upstream's GOAWAY landed between the pre-flight PING and the send — with `REFUSED_STREAM` (RFC 9113 §8.7: closed prior to any processing) or, on node 24 / 26 and Bun 1.4, with an asynchronous `ERR_HTTP2_GOAWAY_SESSION`; a server at its stream limit refuses the same way. Both went through the stream-error path, where only a safe method is replayed, so a POST failed with a 503 although nothing had been processed. The request is now re-sent within the retry budget — on a fresh session, or on the same healthy one when the upstream merely refused a stream. Pickup: bundle restart, no re-bake (#B630, #B631)
* A model-loading failure on an asynchronous connector now aborts the boot with exit code 1 and the reason on stderr, as it already did on a synchronous one. An entity file the class-name check rejects (a name starting with a digit or an underscore), or an entity constructor that throws, on a connector such as DuckDB or Couchbase did not stop the boot: depending on the connector, the failure was logged as an unhandled promise rejection, reported as a failure to connect and retried, or swallowed, and the bundle never listened. Under `gina-container` a DuckDB bundle exited with code 0, a success status. It now ends with `[ FRAMEWORK ] Model loading failed — aborting boot: <cause>` (#B617)
* After a Couchbase reconnect rebuilds the models, each connector now receives the scope declared on its `connectors.json` entry, as it does at boot. The rebuild used to omit it, so a connector whose entry declares a scope other than `NODE_SCOPE` switched to `NODE_SCOPE` for the documents it stamps and the queries it filters. (#B624)
* A Couchbase entity `bulkInsert` now writes the bucket name into its statement as an escaped identifier, so it works on a bucket whose name needs escaping in N1QL, such as `beer-sample`. The name used to go into `INSERT INTO` and `RETURNING` bare, and a dash, which Couchbase allows in a bucket name, made the statement fail to parse. The statement text changes for every bucket (the name is now backtick-quoted); the query means the same. (#B616)
* Bundle-to-bundle `self.query()` calls over HTTP/1.1 now reuse their connections. Each call used to build its own connection pool and throw it away, so every call opened a new TCP connection (500 sequential calls to one bundle opened 500); calls to the same upstream now share one keep-alive pool, kept for the life of the bundle (the same 500 calls use one connection). Each upstream gets its own pool, so a `bundle@project` call still reaches its own upstream, and two upstreams, or one host reached with two CAs, never share one. `maxSockets` (default 100) now limits the concurrent connections to one upstream, which it never did before: a call beyond the limit waits for a free connection, and its `requestTimeout` starts once it has one. At most 50 pools are kept per process; the least recently used one is retired without cutting a call in flight. HTTP/2 calls are unchanged. Pickup: bundle restart, no re-bake (#P44)
* An https `self.query()` no longer reads its CA file from disk on every call. Each call re-read the file named by `server.credentials.ca` (or the call's `ca` option), about 25 µs per call, and on HTTP/2 even when the call reused a cached session and never needed it. The file is now read once and kept for the life of the bundle; each call checks it with one `stat`, and a file that changed on disk (a Kubernetes Secret volume update replaces it) is read again and used by the very next call, as before. A missing or unreadable CA file fails the call with the same error as before. Pickup: bundle restart, no re-bake (#B633)
* `gina project:add` could lose a scope or an environment it had just registered. With `--scope` or `--env` naming one that did not exist yet, the command started linking gina into the new project and, while that step was still running, registered the new names with `scope:add` and `env:add`. Each of these commands rewrites the registry files in `~/.gina`, so on some runs the new name was missing afterwards from `main.json` or from the project entry in `projects.json`, and the state store logged `database is locked`. The link step now starts only once the rest of the command has finished. (#B647)
* `gina scope:link-local`, `scope:link-production` and `env:link-dev` crashed with "Gina has some troubles with this command" and a stack trace when no project could be determined, such as when run outside a project directory without `@<project>`, or when `@<project>` named a project that is not registered: they looked the scope or environment up in the project before checking it. They now print "Project name is required: @<project_name>" or "[ <name> ] is not a valid project name." and exit 1. Their message for a missing argument also named `scope:use` or `env:use` instead of the command that was run. (#B641)
* `gina scope:link-local`, `scope:link-production` and `env:link-dev` could hang after a successful change: they updated `projects.json` but never exited, and when the CLI was started by its own path (`node <gina>/bin/cli …`, as CI and scripts do) its open log listener kept the process alive. The same commands typed through the installed `gina` launcher were not affected. They now exit once the change is written. (#B648)
### Security
* A request-parsing failure no longer writes the unparsed body or query to the log. The data helper's three parse-failure lines printed the whole document, segment or value verbatim at error level (the body of a malformed `{`-leading request that is not labelled `application/json`, or every parameter of a GET whose serialized query document failed to parse, a password or a token included), and the same lines ship in the browser bundle, so they reached the console too; the isaac query parser warned with a query value the same way. The remaining sites now log metadata only — the helper's document line the input's length, its first character and the error's name, the isaac warn the parameter's name, the value's length and the error's name — never the value, and never the parse error's message, which can quote the input; the two segment-level lines are gone, because a urlencoded value that is not JSON is now kept as text instead of reported (#B588). (#B590)
* A bracket-notation field name whose non-last segment is numeric while its container is not an array (`0[a]=1`, or `a[0][b]=2` after `a[x]=1`) no longer throws inside the nesting helper. The throw was a TypeError on a null slot the helper had just seeded for itself, and from the GET/HEAD `inheritedData` call site it had no try/catch: one unauthenticated `GET /any-url?inheritedData=0%5Ba%5D%3D1` exited the bundle process (measured: exit 143, the next request refused). A urlencoded POST/PUT/PATCH with the same field name answered 500, and the validator's client-side twin threw inside the browser, breaking the whole submission. Such a segment now creates a plain object slot (`0[a]=1` nests as the key `0` holding `a`); every previously non-throwing shape is unchanged. (#B591)
* An `application/x-www-form-urlencoded` POST, PUT or PATCH body is no longer percent-decoded as a whole before it is split, so an encoded `&` or `=` inside a field value or a field NAME can no longer act as a separator and add or override other fields of the request (`role=user&bio=hi%26role%3Dadmin` arrived as `role=admin`, and so did `role=user&a%26role%3Dadmin=x`). The body now follows the standard form algorithm: split on `&`, then at the first `=`, each name and value decoded exactly once, so `field=a%26b` is `a&b`, `field=a%3Db` is `a=b`, a raw `=` inside a value is kept (`token=YWJj==` keeps its padding) and a typed `100%25` (sent `100%2525`) stays `100%25` instead of collapsing to `100%`. A quoted token in a value keeps its quotes (`%22true%22` is six characters, and so is a raw `"true"` in a hand-built body); a value that is a JSON document is parsed as JSON and keeps its own types, so a quoted `"true"` inside it stays a string (a text pass over the whole body used to turn it into a boolean), and under a bracket name it nests (`items[0]={…}` now gives `items` an element instead of a field literally named `items[0]`); a value that merely starts with `{` or `[` is kept verbatim instead of dropped; and a value-less `{`-leading segment no longer replaces the whole body. Bare `true`/`false`/`on`/`null` stay strings on this path, as they always did. Pickup: restart AND re-bake — the helper ships in the browser bundle. (#B588)
* A request field named `__proto__`, `constructor` or `prototype` at the top level of a urlencoded body or a query document is now dropped (and so is a top-level `prototype` key in the JSON payload of a route declaring a DTO, which the same helper re-parses; a plain `application/json` body is parsed as-is and keeps it): assigned flat, a JSON-valued `__proto__` pair swapped the PROTOTYPE of the parsed request object, so `req.post.polluted` read an attacker-chosen value that `Object.keys` and `hasOwnProperty` could not see (the process-wide pollution was already closed by #B446; this is the per-request object). (#B592)
* The Couchbase connector no longer writes caller or configuration values into N1QL statement text unvalidated. A `$N` inside `SEARCH()` was spliced into the statement as a double-quoted string literal with no escaping — a search term containing a `"` made the statement malformed, and the substitution rewrote every placeholder up to the statement's last `)` — and is now bound as a query parameter, which Couchbase documents for `SEARCH()`'s query argument on every server version that has the function. A `$N` written as a field-path segment (`doc.flags.$1`) cannot be bound, so its argument is still written after the dot, but only when it is a string of identifiers separated by dots (`identifier(.identifier)*`); anything else is refused before dispatch with a `TypeError` (code `GINA_COUCHBASE_INVALID_FIELD_PATH`), delivered to the query callback when there is one and thrown otherwise. The scope written for `$scope` and stamped as `_scope` on inserted documents is now resolved once when the connector loads and must match `^[A-Za-z0-9_./-]+$` (letters, digits, `_`, `.`, `-` and `/` — the `/` so that a scope registered under the retired `scope:add <bundle>/<scope>` form keeps booting); otherwise the bundle refuses to boot (code `GINA_COUCHBASE_INVALID_SCOPE`, exit code 1). Behaviour changes inside `SEARCH()`: a non-string search term is no longer turned into a string, a value parameter following the call keeps its real type, and a statement compiles one prepared plan instead of one per search term. (#B608)
* `gina project:add` no longer passes `--scope` or `--env` through a shell. When either value named a scope or an environment that was not registered yet, the command registered it by running `scope:add` or `env:add` through a shell command line with the value spliced in unquoted, so shell syntax in the value ran as a command, as the user running `project:add`. Who was exposed: automation that builds these flags from data it does not control, such as a branch or ticket name, and runs `project:add` with them; the second shell parse defeated that automation's own quoting. Typing the command yourself crossed no boundary, and `project:import` was never exposed: it refuses a project that is not registered, and for a registered one the CLI already refused any value that project does not list, before any child could run. `project:add` now checks both values with the scope and environment name rules before anything is written, so an invalid one is refused with exit 1 and no longer leaves the project half-added, and the child commands are started from an argument vector. `project:import` skips that check, so a name registered by an older release, which the rules may now reject, keeps importing. (#B640)
* The Couchbase connector no longer has a REST query transport. With `useRestApi: true` on a couchbase entry of `connectors.json`, every N1QL query was sent over plain HTTP to the query service with the cluster credentials in an `Authorization: Basic` header, even when the entry used `couchbases://`, so the credentials travelled unencrypted where the connection was meant to be TLS. Who was exposed: a couchbase connector configured with both `useRestApi: true` and `couchbases://`; the option is off by default and was not documented. The same transport rewrote every single quote in the statement into a double quote and inserted parameter values without escaping, so a value holding `"` or `\` produced a malformed or different query. The option is now ignored, with one warning when the connector connects, and those queries go through the Couchbase SDK like every other query. (#B634, #B623)
* On a bundle whose `server.protocol` is `http/2.0`, a request that arrives over HTTP/1.1 is now held to each route's declared `method`. Such a bundle also serves HTTP/1.1 through the HTTP/2 server's `allowHTTP1` fallback: a client that does not negotiate HTTP/2, or a reverse proxy that talks HTTP/1.1 to the bundle (nginx's `proxy_pass` does). The router read the request method from the HTTP/2 `:method` pseudo-header whenever the bundle was configured for HTTP/2, and an HTTP/1.1 request carries none, so every method passed the method checks. Any method then ran a single-method route whose URL has no `:param` segment, and any method ran a multi-method route, parameters or not: a GET reached a POST-only action (and a GET is never asked for a CSRF token), a DELETE ran a `GET, POST` route, and a POST on a URL declared for both GET and POST ran whichever route was declared first. The route cache is keyed by method and path, so one such request also left the wrong action as the cached answer for every later client using that method on that path, HTTP/2 clients included, until a restart or until the entry was evicted — and a client could evict it with enough requests to any route that takes a parameter. Single-method routes with a `:param` segment were not affected, nor were bundles on the default `http/1.1` protocol. An HTTP/1.1 CORS preflight on such a bundle is now answered 204, as an HTTP/2 one is; it used to be routed, and the route's action ran for the OPTIONS request. Pickup: restart. (#B645)
* A query key named like a member every object inherits — `toString`, `valueOf`, `toLocaleString`, `isPrototypeOf` — no longer counts as a route requirement. For a GET or DELETE request on a route that declares `requirements`, the router treats each request key that names a requirement the URL does not bind as a whole `:key` segment as an extra URL variable, and it looked the name up with a plain property read, which also finds those inherited members. Each such key, with a value shaped like that member's source text, replaced one leading segment of the compared URL — the first the always-empty leading position, the second the bundle webroot, the next ones the path — so a request reached a route whose path differs from its own, including a path outside the bundle's webroot, and the action received `req.params.toString` as a string. A path-based control applied outside the route, such as a reverse-proxy location rule, could be bypassed this way; the reached route's own middleware and authorization still ran. Only requirements a route declares itself now count. Every release since 0.1.0 is affected, on Node.js and on Bun. Pickup: restart and re-bake. (#B650)
