## 0.7.0 - 2026-09-27
### Added
* A Swig bundle that leaves `settings.swig.autoescape` unset now gets a warning at boot, once, naming 0.8.0: in 0.8.0 the default becomes `true`, which HTML-escapes every `{{ x }}` a template does not mark `| safe`. Set the key explicitly to keep your bundle's behaviour and silence the warning: `true` to escape (then mark a variable that carries HTML on purpose with `| safe`, for example `{{ gina.csrfInput | safe }}`), or `false` to keep output unescaped. A bundle whose own pages render only through Nunjucks is not warned. New bundles created with `gina bundle:add` now set `"swig": { "autoescape": true }` in their `settings.json`. Rendered output does not change in 0.7.0. Pick it up with a bundle restart. (#B359)
* A bundle now warns once at boot, in one line, about the routing `requirements` regexes that are not anchored at both ends, such as `"/[0-9]+/"`. A requirement is tested as a partial match when a request is matched, so that one accepts `123abc`: anchor it (`"/^[0-9]+$/"`) to constrain the whole value, or write an intended partial match in full (`"/^pk_.*$/"`). A pattern with the `m` flag counts as not anchored, and each alternative of a `|` must be anchored. Requirements are never changed, and they are not applied when a URL is built: `lib.routing.getRoute()`, its `toUrl()` and the `getUrl` template filter put parameter values into the path as given. Pick it up with a bundle restart. (#B360)
### Changed
* Route matching no longer evaluates every rule of a bundle for a request the warm route cache has not seen. Once per routing table, the engine indexes which rules could match a URL: segment count, static segments, parameters (a `:` anywhere in a segment, so inline parameters included), each variant of a comma-separated URL, and each rule's raw `url`. The declaration-order scan then skips every other rule, so the first matching rule still wins and every per-rule check (scope, method, requirements) runs as before, and a request no rule can match gets its 404 without a scan. Measured on the routing step alone, over a 380-rule table: matching a late rule went from about 440 µs to about 14 µs, and a 404 from about 510 µs to about 12 µs. Some requests and rules are still scanned in full: the root path, a path with a trailing or doubled slash, a path holding `?` (the express engine keeps the query in the path), and a rule declaring two or more `requirements` that are not bound to a whole `:key` segment of its `url`. A rule the index skips no longer runs its requirement checks for that request. A `validator::` requirement on such a rule is no longer evaluated, so a malformed one no longer answers 500 for other URLs, and a `validator::{ query: ... }` no longer sends its backend request. On a 404 or a 405, `req.params` also no longer carries values that a skipped rule used to capture. Pickup: bundle restart, no re-bake (#P46)
* The warm route cache, the per-process record of which rule matched each `METHOD:path` pair (up to 5,000 of them), is now one `Map`. A lookup and an eviction cost the same at any size: with the cache full, a lookup went from 18-74 µs to about 1.5 µs, and an insert that evicts the oldest entry from 26-80 µs to about 1 µs (two runs on a loaded host). The rules are unchanged: the first write to a key wins, the oldest key is evicted first, and a hit does not move an entry. A cache entry now keeps only the rule's name and object. It used to also keep the route parameters and the data of the request that first matched it (for a POST, its body, a login form's included) for as long as the entry lived, which is the life of the process unless 5,000 other paths pushed it out. The unused radix trie is removed: `lib/routing/src/radix.js` and the routing library's internal `buildTrie()` and `lookupTrie()`, which no running code called (the route candidate index replaces them). Pickup: bundle restart, and a re-bake to carry the rebuilt browser bundle (#P46)
* Over HTTP/2, `self.query()` no longer adds `status: 200` to an upstream JSON body that carries no `status`, and no longer logs `Response status code is undefined: switching to 200` on every such call. The caller receives the body as the upstream sent it, as it always did over HTTP/1.1, and so does the end client of a `control: "forward"` route, which relayed the added key. Success is decided as before: a body without `status` is a success on both transports, and a body that carries one, numeric or not, is delivered unchanged. A JSON string body such as `"[]"` is now a success over HTTP/2 too; the added key threw on it and the call answered 500. Code that read `status` on such a result now reads `undefined` and should treat an absent `status` as success, as the framework does; code that deleted the added key no longer needs to. Pickup: bundle restart, no re-bake (#P47)
### Fixed
* `gina project:rename @<old> @<new>` refused every free name as already taken and renamed only onto a project that was already registered, and that rename damaged the port records: another project whose name began with the old one had its `ports.reverse.json` entries renamed too, and the renamed project kept its old name in `ports.json` beside stray entries. It now renames to a free name, refuses a registered name or an existing directory with exit `1` before anything moves, and renames port entries only where the project name matches exactly. (#B651)
* `gina env:add <env> @<project>` registered the environment on the project but never gave its bundles ports for it or wrote their `env.json` blocks, so the new environment could not start; it also printed nothing, and it hung wherever the CLI was started by its own path. It now gives every bundle of the project its own ports for the environment, writes the `env.json` blocks, prints `environment [ <env> ] created` and exits; a failure rolls its changes back. (#B643)
* A failed file copy through the path helper (`_().cp()`, `PathObject.mv()`, which CLI copy, build and rename paths use) could leave its temporary `*.tmp` file beside the destination: the temporary file was removed only if it existed when the failure was reported, and its creation could finish just after. It is now removed once its stream has closed, before the callback runs. (#B649)
* On Bun, a failed file copy through the path helper reported an Error with no `stack`, so callers that print `err.stack` printed `undefined`. The error now always carries a stack, and keeps its code and message. (#B654)
* Six more commands never ended the process after doing their work, so they hung wherever the CLI was started by its own path (as CI and scripts run it): `gina port:reset` with no registered project, `env:unset`, `env:set` with no key, `port:list --format=json` (with or without `--filename`) and `--format=conf` without `--filename`, `connector:list` without `@<project>`, and a cancelled `protocol:set` prompt. They now exit; the listings exit only once their output has been written. (#B653)
* `gina project:add` and `project:import` read `--path`, `--scope` and `--env` whole. A value holding `=` was cut at its second `=`: on a fresh registry a `--path` holding `=` failed with `ENOENT`, `project:import` refused such a path as one that "no longer exists", and `--scope=a=b` or `--env=a=b` registered `a` instead of refusing the name. A `--path` value containing `--scope=` or `--env=` is no longer read as that flag, and a failed removal of the project's `node_modules/gina` link now reports its own error instead of a `ReferenceError`. `--scope` and `--env` register a missing scope or environment; they do not change the project's defaults, which `scope:use` and `env:use` set, as the CLI reference now says. (#B644)
* The `connectors.json` a new bundle is scaffolded with showed the Couchbase keep-alive interval as `ping`, a key the connector ignores. Its example now names `pingInterval`, the key the connector reads (default `2m`, used while `keepAlive` is on, as it is by default). (#D51)
* A first `npm install -g gina` no longer fails when your home directory, or the npm prefix, has a space in its path. The install scripts ran `chown` on `~/.gina` (a no-op, now removed) and created and sourced `~/.profile` through command lines with the path unquoted, and aborted; the sourcing never reached your shell either, so it is removed and a new shell reads the profile. The install's npm probes and `framework:set` calls also reach such paths whole now, where before they failed without a word. `gina port:reset` reads the project's bundles itself instead of running `gina bundle:list` through a shell, so it no longer crashes when `gina` is not on your `PATH` or sits under a path with a space, and it no longer consults whichever `gina` comes first on `PATH`. `gina bundle:restart` runs `bundle:stop` and `bundle:start` without a shell, so it works from an install under a path with a space and passes each flag through unchanged. (#B663)
* On the Express engine, a URL carrying a query string never matched a route or a static file, on Express 4 and 5 alike: `GET /items?page=2` answered 404 while `GET /items` answered 200, and a static requested with a cache-buster (`/css/app.css?v=3`) was not found. The engine kept the query string in `request.url`, so the path handed to route matching, to the statics handler and to the requirement matcher still carried `?…` on its last segment; the built-in isaac engine strips it before dispatch. The Express path now does the same, after the framework's own `/_gina/*` handlers (which read a `?key=` off the full URL) and before the webroot filter, the statics and the routing loop, with the engine's query materialised on `request.query` first. `request.originalUrl` keeps the full URL. A consequence to know: the warm route cache is keyed by method and path, so on Express the query variants of one path now share one entry exactly as on isaac — the match verdict is re-evaluated on every hit. Pickup: bundle restart (#B668)
* A `405 Method Not Allowed` now carries the `Allow` header that RFC 9110 requires, listing the methods of the routes whose URL matched, with `HEAD` wherever `GET` is listed; a wrong method on a URL whose routes each declare a single method still answers 404, as documented. A `HEAD` request is now served by every route that serves `GET`: it used to answer 404 on a parameterised URL (a `GET` route on `/items/:id`) and 405 on a route declaring several methods (`"GET,POST"`), and only a single-method `GET` route on a static URL served it. On the isaac engine the `access-control-allow-methods` header of a `HEAD` response now reads `HEAD` rather than `GET`, as it already did on the Express engine. Pickup: bundle restart (#B659, #B667)
* A `HEAD` request served by a route that serves `GET` now gives the action the same `req.get` a `GET` would, so a `GET` action that reads `req.get` no longer answers 500 on `HEAD`. gina runs the `GET` action for a `HEAD`, so that the response carries the headers a `GET` would, but it kept the request's URL and query parameters only in `req.head` and left `req.get` undefined, and an action reading `req.get.<param>` threw. `req.get` is now the same object as `req.head`; `req.head`, `req.getParam()` and `req.getParams()` are unchanged, and `req.method` stays `HEAD`, so the response still has no body. Affected: 0.3.0 to 0.6.33, on routes with a static URL (a `HEAD` on a parameterised or multi-method route answered 404 or 405 there). Pickup: bundle restart (#B675)
* The first gina commands after moving to a new minor version (for example 0.6 → 0.7) no longer fail. On that first run, gina copies each per-version default it keeps in `~/.gina/main.json` (culture, timezone, log level, protocols, scopes and the rest) from the previous minor version to the new one. The copy ran only while the new version was not yet registered in that file, and `gina bundle:start`, `bundle:restart`, `project:start` and `project:restart` register it before the copy runs, as does every `gina-container` boot. When one of those came first, the copy never ran and every later gina command exited 1 with `Cannot read properties of undefined (reading 'split')` until the file was repaired by hand. The copy now fills whatever the new version is missing, whether or not the version is registered, and keeps any entry already there. Separately, even when the copy ran, the first command exited 1 once with `(reading 'indexOf')`, because the later steps of that same command still read the file as it was before the copy; they now read the updated file. Exposed: installs that skip npm's install scripts (Bun, `gina-container` images, a git checkout); an npm install ran the copy first. CLI only: nothing to restart. (#B680, #B681)
* With `settings.swig.autoescape: true`, a Swig page now keeps its CSS and JavaScript. Gina injects the bundle's stylesheet and script tags into the layout through the `{{ page.view.stylesheets }}` and `{{ page.view.scripts }}` placeholders, and auto-escaping rendered every injected `<link>` and `<script>` tag as visible text, so the page lost all its styles and scripts. The placeholders are now injected with `| safe`, and a layout that already holds either one, bare or with `| safe`, is not given a second copy. With autoescape on, the `nl2br` filter also escapes the text it receives and keeps its line breaks as markup; before, the `<br/>` it added showed as text. With autoescape off (the default until 0.8.0) rendered output is unchanged. A layout that places `{{ page.view.stylesheets }}` or `{{ page.view.scripts }}` itself writes `| safe` when autoescape is on, as with Nunjucks. Pick it up with a bundle restart. (#B690, #B359)
### Security
* On the Express engine with Express 5, one request could stop the bundle: a DELETE, or a POST, PUT or PATCH sent without a body, on any URL, before routing and with no authentication. The Express 5 support added in 0.6.9 shadowed Express's `req.query` getter with a plain writable property so the framework's own assignments would work, but that left `request.query` undefined until the GET and HEAD branches assigned it; the DELETE branch and the empty-body fallback of the body-carrying branches counted it as it was, and the resulting TypeError inside the request's end handler took the uncaught-exception path and exited the process. The property is now an accessor: on the first read it materialises Express's own parse — honouring the app's `query parser` setting at read time — as a plain, writable object of the request (a plain copy, because the default `simple` parser returns a null-prototype object that the framework's `count()` helper cannot iterate), and assignments still store. Express 4, where the query middleware assigns the property on every request, and the default isaac engine were never affected. No layer is registered and no router is created at engine construction, so an `app.set(...)` made in `onInitialize` keeps its effect. Affected: `>= 0.6.9 <= 0.6.33` with `engine: "express"` and Express 5 installed. Pickup: bundle restart (#B666)
* A plain `GET` no longer runs an action whose route is declared `"method": "DELETE"`. So that the popin and link plugins could send their anchors as a `GET`, the router served any `GET` to such a URL as a `DELETE`, for any client. A cross-site navigation carrying the visitor's session cookie could therefore run a `DELETE` action: on the Express engine even with the Csrf plugin adopted as documented, because the plugin runs before routing and treats a `GET` as safe (the default isaac engine refused it), and on either engine when the plugin is not used, since the Session plugin's default `SameSite=Lax` cookie is sent on a top-level cross-site navigation. The override is now granted only to an XHR (`X-Requested-With: XMLHttpRequest`) that is not a browser cross-origin request: a `Sec-Fetch-Site` of `same-origin` or `none` passes, `same-site` and `cross-site` are refused, and an `Origin` that differs from the host is refused. Any other `GET` answers 404 on a URL whose only route is `DELETE`, and 405 on a route whose method list includes `DELETE`. The override now sets the request method to `DELETE`; on a route declaring several methods it used to hand the action the whole list (`req.method === "POST,DELETE"`). Client code that sends a `GET` to a DELETE-only route from outside the bundle's own pages, or without the header, must send a real `DELETE`. Affected: every version up to 0.6.33, on both engines. Pickup: bundle restart (#B662, #B660)
* A controller's `self.throwError()` no longer sends a stack trace passed as the message to clients outside the local scope. A call such as `self.throwError(res, 500, err.stack)` or `self.throwError(500, err.stack)`, or an error object whose `message`, `error` or `title` holds a stack, put the file paths and frames in the JSON body and on the built-in HTML error page in every scope, because only the `stack` field was stripped. Outside the local scope such a value now keeps its first line in the JSON body, on the fallback page and in the data a custom error page receives, and the full text goes to the server log line that carries the incident ref. On the HTML path that line now logs the error's own text rather than the `throwError` call site, and a `self.throwError(res, code, { ... })` call now writes one at all (it logged no line for its ref before). Local scope is unchanged. The engine-level error responder has done the same since 0.5.21. Affected: every version up to 0.6.33. Pickup: bundle restart (#B670)
* The browser bundle ships no dynamic-code call any more. A custom form validator (`forms/validators/<name>/main.js`) is compiled by the browser as an inline script carrying the page's own CSP nonce instead of through eval: same scope contract (`this.getValidationContext()`), same name in DevTools, one compile per validator per page, and no 'unsafe-eval' needed. The two unreachable calls the bundled RequireJS (`require.exec`, the transpiler-plugin path) and engine.io-client (its global-object shim) carried are rewritten at build time by exact match, so a dependency bump that moves them fails the build instead of shipping them. On the server, where custom validators are not wired, a function registered on the gina context is attached as it is. Supply-chain scanners flagged the eval on some published versions and not others, which swung the package score between two values on identical bytes (#M21d)
* The start command that `gina tail --follow` re-runs when a bundle crashes is now saved under the framework home (`<GINA_HOMEDIR>/run/<bundle>@<project>.argv`, `~/.gina/run/` by default, written with mode 0600) instead of the system tmp directory, and on POSIX systems it is re-run only when that file is a regular file owned by the current user that group and other cannot write; any other file is refused with a warning. Where the tmp directory is shared between local users (`/tmp` on Linux by default), another user could create the file first: the owner's own `gina bundle:start` then failed to overwrite it, and the next crash restart ran that user's program under the owner's account. Affected: every version up to 0.6.33. Pickup: restart `gina tail`, then start each bundle once so its file is written in the new place; until then a crashed bundle is not restarted automatically (#B676)
* The framework log listener (the MQ listener on port 8125, loopback by default) no longer stops the framework daemon when a connecting client sends a log frame whose `request` field names an inherited object member (such as `__proto__` or `constructor`) or the listener object's own `name` field: such a value reached an array method on a non-array, or a call on a non-function, and threw out of the socket handler, ending the daemon process that also serves the command socket on 8124. The listener now accepts only a short identifier as a request name and dispatches only to its own methods, refusing any other frame with a warning and keeping the connection and the process. The listener binds loopback by default, so this was reachable only by a process on the same host. Affected: every version up to 0.6.33. Pickup: framework restart (#B678)
* On the default (isaac) engine, a request carrying a very long `X-Forwarded-Prefix` header no longer ties up the bundle: the mount-path length and character-set check now runs before the trailing-slash trim, so an over-length value is discarded before any regular expression sees it. The trim used a pattern that backtracks quadratically on a long run of slashes, and it ran on the raw header on every request, so one request with a 15 KB header cost roughly 100 to 170 ms of CPU (about 8 seconds at the 64 KB an HTTP/2 header list admits) — enough for a few such requests a second to saturate a single-threaded bundle. A legitimate mount path (at most 255 characters) is unaffected; anything longer is ignored as before. Affected: every version from 0.3.10 to 0.6.33 on the isaac engine. Pickup: bundle restart (#B679)
