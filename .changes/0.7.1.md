## 0.7.1 - 2026-10-01
### Changed
* A new project or bundle name must now be made of letters, digits, `_`, `.` and `-`, and start with a lowercase letter, a digit, `_` or `.`; `.`, `..` and the names every object inherits, such as `constructor`, are refused. `project:add`, `bundle:add`, the new name given to `project:rename`, `bundle:rename` or `bundle:copy`, and the name `project:restore` registers are checked before anything is written, and `bundle:add` checks every name of its list before it adds the first bundle. Until now only the first character was checked, so names holding spaces, quotes, `$` or `/` were registered, and `project:add @constructor` took the name for a registered project with no path and failed. A project or bundle already registered under a name outside the rule keeps working, including with `project:import`, `bundle:add --import` and `bundle:add --replace`. (#B665)
* The global `setContext()` and `getConfig()` helpers no longer resolve the merge library on every call: it is bound once when the helpers load. Each call paid a full module resolution, about 3 µs, and the router makes two such calls per routed request.
* In production the router probes a bundle's `controllers/setup.js` once, when the bundle first serves a request, instead of on every request; in development the per-request probe stays, because the file is re-read there when it changes. The probe cost two thrown file-system errors per request whenever the file was absent.
* A routed request no longer builds three throwaway configuration objects. Resolving the route, deciding whether the bundle has views and matching the request to a bundle each constructed a new configuration object only to read the one already loaded; they now read the loaded configuration directly once it is initialised, and the views check consults its per-bundle answer before anything else. Before initialisation, the calls run as they did.
* A routed request of a bundle with views no longer re-encodes the bundle's forms catalog, re-reads the V8 heap limit or stamps the date twice. The encoded `page.environment.forms` export is kept per catalog and reused (the catalog is loaded once per bundle; a large catalog cost about 5 µs per KB on every such request, JSON routes included), the `memory allocated` label is computed once, and `page.environment.date.now` and the locale's `date.now` now carry the same timestamp. Render data that writes into `page.forms`, which holds the shared catalog, no longer changes the forms export of later requests.
* The controller's `set()`, which fills the render data about 60 times on every routed request of a bundle with views, tests for and splits dotted names with string operations instead of regular expressions. Behaviour is unchanged.
* Constructing a class built with `inherits()` — every controller, on every routed request — no longer copies anything onto the instance: no own `prototype` property (it was enumerable, so it showed in `Object.keys()` and `JSON.stringify()` of an instance), no stamp of the instance's name onto a shared prototype on every construction, and no copy of the parent prototype's falsy members as own properties. Inherited members resolve through the prototype chain as before, and the browser bundle carries the same constructor.
* Each bundle's resolved environment configuration now stays in V8's fast property mode. Loading it left the object in dictionary mode, which made the router's per-request copy of it cost about 20 µs; the copy now costs well under 1 µs, and the request's reads of the configuration are faster too. The configuration's contents are unchanged.
### Fixed
* `gina project:start`, `project:stop` and `project:restart` now work from an install whose path holds a space: they ran `bundle:start`, `bundle:stop` or `bundle:restart` through a command line that split the path, and failed. A `bundle:start` that reinstalls a project's `node_modules` after an architecture or platform change re-links gina with the running install's own `bin/gina`, so it no longer fails when `gina` is not on your `PATH`, nor uses whichever `gina` comes first there. A flag value holding a space now reaches the `link` steps of `project:` and `bundle:` start, stop and restart as one value instead of two. When a bundle's pid file is missing, `bundle:stop` finds its process by the exact `gina: <bundle>@<project>` title: `api@shop` no longer matches the process of `api@shopping`, which it could stop instead. (#B665)
* A bundle started through the framework daemon now shows its boot warnings in the output of `gina bundle:start`, and of `gina bundle:restart`, which prints its start step. Every line the bundle logs at `warn`, `warning`, `error`, `err`, `crit` or `alert` while it starts is written there, before the started line. Until now these lines reached only a `gina tail` already attached when the bundle booted, because the log listener keeps no backlog: running `gina bundle:start` and then `gina tail`, or a container whose init script starts the bundle before its tail, never showed them, including the two boot warnings added in 0.7.0 (Swig `autoescape` not set, and unanchored routing `requirements`). A tail attached before the start still receives these lines, so each one then appears twice. An `emerg` line keeps its `aborted` message, and lines logged after the start still reach only the tail. Restart the framework to pick this up: `gina framework:restart`, or restart the container that runs the framework. (#B691)
* `bin/gina` no longer loses the command when a `--restart-pid` flag is passed: its filter removed the runtime path from the arguments instead of the flag, so `gina start --restart-pid=<pid>` lost its `start` task, and any other command reached the CLI shifted by one argument. The flag belonged to an internal restart handshake that nothing used any more, so its handling is removed: a typed `--restart-pid` is now passed on like any other flag. (#B689)
* `bundle:stop` reads a bundle's pid file as a positive integer only: a pid file holding `-1` made it send `SIGKILL` to every process the user could signal, and one holding `12abc` to pid 12 (#B693). On a host without `ps`, such as a slim container image, `framework:status` no longer removes the pid file of every running framework: it checks each pid with a signal-0 probe instead of `ps -a`. `gina .` and `framework:open` now open a directory whose path holds a space instead of splitting it in two, and `framework:build` passes each of its arguments to the build script whole. An isaac bundle whose cache path holds a space now gets the brotli and gzip copies of its routing files: the compressions split the path and failed.The npm prefix look-ups that the CLI bootstrap and `framework:init` fall back on when no prefix is configured no longer fail when npm is installed under a path holding a space. (#B665)
* A `getConfig()` or `getLib()` call that names no bundle no longer walks the call stack when it does not need to: `getConfig()` and `getConfig(confName)` resolve to the running bundle without it, and where the walk is still needed (`getConfig(<falsy>, confName)`, `getLib(lib)`) the stack is captured once instead of once per frame examined. When no frame outside `node_modules` qualifies, the call now takes the no-match path instead of throwing a TypeError. On an npm install, every request to a bundle with templates used to pay up to nine stack captures and a caught exception in the render setup, about a quarter of a request's CPU in a profile of a trivial JSON route; the render setup now reads the bundle's Swig settings from the request's own configuration. (#B695)
* Port lookups no longer take a bundle or project for another whose name begins with it or extends it. `bundle:remove api @shop` also removed the ports of `myapi@shop` and the port registry entry of `api@shopping`; `port:reset` removed the ports of the same bundle in a project whose name begins with its project's; while allocating ports, `bundle:add`, `bundle:copy` and `env:add` could give environment `dev` the port assigned to `devel`, taking it from `devel`; and `project:add` and `port:reset` could skip an assignment as already made because another value contained it (`api@shop/dev` inside `api@shop/devel` or `myapi@shop/dev`). The first-character refusal of `bundle:add` also names the rejected bundle instead of printing `[ undefined ]`. (#B665)
* The built-in engine looks the output cache up only while `server.cache.enable` is on. With the cache disabled it looked every GET up anyway, two file-existence checks per request, and could serve a page left on disk by an earlier run that had caching enabled.
* The path helper no longer records every distinct path it normalizes. Each `_()` call added the path to a list kept for the life of the process, and each `_()` call and each path object's `toString()` searched that list, so a bundle's memory and per-call CPU grew with the number of distinct paths it had ever seen: two per distinct request URL, query string included, through the output cache's file paths. Nothing read the list. `toString()` and `toUnixStyle()` return exactly what they did. `toWin32Style()` now also converts a path whose trailing separator `mkdir()`, `mkdirSync()`, `rm()`, `rmSync()` or `isValidPath()` had stripped, which it used to return with forward slashes (#B703)
* On the isaac engine (the default), the storage maintenance endpoints of a running bundle now read their query string. Isaac removes the query from the request URL before handing a request to the handlers behind `/_gina/storage/stats`, `/_gina/storage/gc` and `/_gina/storage/verify`, which read `?driver=` and `?dryRun=` from that URL and so never saw them: against a running bundle, `gina storage:gc --dry-run` ran a real garbage collection, removing every unreferenced blob past `sweepGrace` on every `cas` driver (including one whose automatic sweep is off, `sweepInterval: 0`), and `--driver=<name>` was ignored by `storage:stats`, `storage:gc` and `storage:verify`, which reported on or collected every driver. The handlers now read the query from the original request URL. A stopped bundle (the CLI then opens the store itself) and the express engine were not affected, and the endpoints still answer only callers listed in `app.json` `admin.allowFrom`. Affected: 0.6.7 through 0.7.0. Pickup: restart the bundle; nothing to re-bake (#B710)
* A client listed in `server.maintenance.allowFrom` now gets through a maintenance window on an isaac bundle whose `server.protocol` is http/1.1, the default engine and protocol. The isaac engine's maintenance gate admitted it, then rewrote the request's `Host` without its port before handing it on, and the second maintenance check read that port-less `Host` as the sign of a reverse proxy, closed the address arm and answered 503: the documented IP bypass never let a listed operator reach a page or a static file. The second check now honours the isaac gate's verdict instead of deciding again. A bundle serving HTTP/2 (whatever protocol its clients speak), the Express engine, the `bypassKey` header and cookie, and `server.proxy.requireForwardedHeaders: true` were not affected. A reverse proxy on the bundle's own host that forwards the `Host` with its port and adds no forwarding header cannot be told from a direct client, so a request it relays from a listed address passes too, as it already did on a bundle serving HTTP/2 and on Express. Affected: 0.6.10 through 0.7.0. Pickup: restart the bundle; nothing to re-bake (#B711)
* During a maintenance window on the isaac engine, `/_gina/storage/stats`, `/_gina/storage/gc` and `/_gina/storage/verify` answer again. They exist only in the engine-agnostic server layer, and the isaac engine's maintenance gate, which lets through every `/_gina/*` endpoint the engine answers itself, stood in front of them: `gina storage:stats`, `storage:gc` and `storage:verify` failed against a running bundle for the whole window, reporting an invalid response. A health check whose URL carries a query string (`/_gina/health/check?probe=1`) got the maintenance 503 on isaac for the same reason. The isaac gate now lets those exact paths through to the server layer, where the storage endpoints stay restricted to `app.json` `admin.allowFrom`. The storage endpoints were not affected on the express engine; a health check with a query string was, in and out of a window, and is fixed by #B717. Affected: 0.6.10 through 0.7.0. Pickup: restart the bundle; nothing to re-bake (#B715)
* On the express engine, a `POST /_gina/maintenance` or `POST /_gina/instrument` carrying a JSON body no longer stops the bundle. The server layer sets an encoding on every non-multipart request, so the body arrived as text, and the reader of these small control bodies threw while joining it: an uncaught exception that ended the process. The reader now accepts text, counts its 4 KB cap in bytes and reports a failure through its callback. Only a caller the endpoint already admits could send it: an address in `app.json` `admin.allowFrom` for the maintenance toggle, the inspector key for the instrumentation window. The isaac engine was not affected. Affected: 0.6.10 through 0.7.0 for `/_gina/maintenance`, 0.4.0 through 0.7.0 for `/_gina/instrument`. Pickup: restart the bundle; nothing to re-bake (#B714)
* `/_gina/health/check`, `/_gina/assets/routing.json`, `/_gina/release/status` and `/_gina/release/events` answer a URL that carries a query string. They matched their path only when the URL ended there, so the same path followed by a query string (`/_gina/health/check?probe=1`) missed the endpoint: on the express engine it fell through to routing, a 404 (or the maintenance 503 during a window), and on the isaac engine the routing map and the release-watch endpoints with a query string answered the maintenance 503 during a window. The four endpoints now ignore a query string on both engines, and the isaac engine's routing-map fast path looks its asset up by the file name it matched. The browser fetches the routing map without a query string, so pages were not affected. Pickup: restart the bundle; nothing to re-bake (#B717)
* `/_gina/health/check` answers `HEAD` on both engines: the `200` and the headers a `GET` gets, plus `content-length`, and no body. It answered `GET` only, so a `HEAD` probe, which some load balancers and monitors send, fell through to routing: a 404, or the maintenance 503 during a window. Pickup: restart the bundle; nothing to re-bake (#B718)
* A page whose query string ends in a `/_gina/` endpoint path is answered by the page again. The built-in endpoints that #B709 left out of its exact-path matching (the health check, `/_gina/jobs/<id>`, `/_gina/instrument`, and the dev-only `/_gina/inspector`, `/_gina/logs`, `/_gina/agent`, `/_gina/indexes` and `/_gina/reveal`) tested the whole URL, so a URL such as `/web/?next=/_gina/health/check` got the endpoint's answer instead of the page, on both engines, outside a maintenance window and inside one, where the page's 503 was due; a WebSocket upgrade to such a URL was taken by the Inspector agent. These endpoints now match the URL's path only, keeping their prefix tolerance, letter case, methods and gates. The dev-only `/_gina/inspector`, `/_gina/logs`, `/_gina/indexes` and `/_gina/reveal` also answer a URL that carries a query string (`/_gina/logs?x=1`): on the express engine it missed them (a 404, or the maintenance 503 during a window), and on the isaac engine it got the maintenance 503 during a window. Pickup: restart the bundle; nothing to re-bake (#B712)
* The isaac engine's own event streams answer HTTP/2 clients: `/_gina/logs` and `/_gina/agent` (the Inspector's server-log and agent streams) and `/_gina/release/events` (the live release-watch banner). Each sent a `connection: keep-alive` header, which HTTP/2 forbids: node refused the response headers (`ERR_HTTP2_INVALID_CONNECTION_HEADERS`, logged as a warning) and the client never got an answer, so an `http/2.0` bundle reached directly over HTTP/2 streamed none of them. HTTP/1.1 clients, including a proxy that talks HTTP/1.1 to the bundle, were not affected. The header now goes to HTTP/1.1 clients only. Affected: 0.3.0 through 0.7.0 (`/_gina/release/events`: 0.5.18 through 0.7.0). Pickup: restart the bundle; nothing to re-bake (#B722)
* The standalone Inspector and `gina inspector:open` accept a target URL that carries a query string or a fragment. The Inspector appends `/_gina/<endpoint>` to its `?target=` value, and the command passes a URL argument through as that value, so a pasted page URL such as `http://localhost:3100/page?x=1` built `http://localhost:3100/page?x=1/_gina/agent`: the endpoint path landed in the query string, where the endpoints no longer look for it (#B712), and outside dev mode the agent key became part of another parameter. The target's query string and fragment are now dropped, then its trailing slashes. Pickup: the bundle reads the Inspector from the framework on every request, so reload the Inspector window, with nothing to restart or re-bake; the command takes effect on its next run (#B719)
### Security
* CLI commands that start other gina commands, or look up bundle processes, no longer build shell command lines. `project:start`, `project:stop` and `project:restart`; the `link-node-modules` and `link` steps that run on every `project:` and `bundle:` start, stop and restart; the `framework:link` step of a `bundle:start` that reinstalls a project's `node_modules`; the `node_modules` repair step of `framework:link`; and the process lookups of `bundle:stop` and `minion:kill` all spliced the project or bundle name, and the forwarded `--` flags, into a command line run by `sh`, unquoted or inside single quotes, so shell syntax in a registered name or in a flag value ran as a command, as the user running gina. Who was exposed: automation that builds these names or flags from data it does not control and runs the commands with them, and anything that can send a `bundle:start` to the local framework daemon, which already runs any framework command for whoever reaches its socket (loopback only by default). Typing a command yourself crossed no boundary. These children now start from argument vectors, and `bundle:stop` and `minion:kill` read the `ps -ef` listing themselves. (#B665)
* More CLI commands no longer build shell command lines. `framework:status`, `framework:restart`, `framework:build`, the download and extract steps of `framework:add`, `gina .`, `framework:open`, the default-browser probes, browser launch and fallbacks of `inspector:open`, and the npm prefix look-ups of the CLI bootstrap and of `framework:init` put values into a command line run by `sh`: the arguments you passed, file paths, the Inspector URL, a pid file's content. Shell syntax in any of them ran as a command, as the user running gina. The isaac engine's brotli and gzip compressions of its routing files, which run at every boot, did the same with the cache path. Each value came from that user's own command line, settings or files, so no boundary was crossed; these commands now start their children from argument vectors, and Windows keeps the command lines that need cmd.exe (`start`, `where` and `npm.cmd`). `framework:status` also listed every user's processes and named a pid file after the title of any `gina-`-titled one, so another local user's process titled `gina-v/../../x` made it write `x.pid` outside the run directory: it now lists the current user's processes only and accepts only a framework daemon's `gina-v<version>` title. (#B665, #B677)
* `settings.swig.autoescape: true` is now applied when gina is installed with npm. A bundle's Swig settings were read on every request through a helper that located the calling bundle by walking the call stack and skipping every frame whose path contains `node_modules`. Under an npm install (a global install, a project dependency, the image built by `gina image:build`) every framework file sits there, so the walk found nothing and threw; the render setup caught the error and continued with auto-escaping off while the bundle's configuration said it was on, and nothing was logged. Affected: 0.5.25 to 0.7.0, npm installs only; gina run from a repository checkout was not. After upgrading, auto-escaping becomes active on such installs for every bundle that sets `autoescape: true`: before upgrading, print `gina.csrfInput` with `| safe` and mark every other variable that carries trusted markup with `| safe` (the 0.7.0 migration checklist). (#B695)
* The CLI now matches project, bundle and environment names literally when it looks them up in the port and project registries. It built regular expressions from the names, so a `.` in a name matched any character, and a name holding `+`, `(` or `[` broke the lookup or made the command throw: `project:remove @my.app` also removed the ports of `my-app`, `env:remove` could remove, and `port:list` list, another project's entries, and `bundle:start` did not recognise the mounted line of a bundle whose name holds `+`, so it waited out its start timeout and stopped the bundle. The install scripts match the install prefix literally too: a prefix holding `c++` made `npm install -g gina` fail. These names come from your own registry and command line, or from what can reach the framework's command socket, which listens on loopback by default. (#B665)
* `run()` (also `gna.run`) and `Shell::run()` in `lib/shell` no longer write every command's output to the fixed files `out.log` and `err.log` in the temp directory (`opt.tmp` / `GINA_TMPDIR`, the system temp directory by default): each run now gets a private directory of its own under that base — created with mode 0700 and an unpredictable name, removed with its two files when the command exits — and a failure while reading the output back is delivered as the run's error instead of leaving the caller waiting. Two runs sharing a temp directory used to read each other's output as their own (the later one received the earlier one's stdout and stderr, the earlier one got nothing), and a run whose files a sibling had already removed never called back. Where the temp directory is shared between local users (`/tmp` on Linux by default), another user could create those names first, which stopped `gina project:add` / `project:import` and any `run()` call on that host, and on hosts without the kernel's `fs.protected_regular` / `fs.protected_symlinks` protections let that user read the command output or have it appended to a file of their choosing. Affected: every version up to 0.7.0. Pickup: the CLI on its next command, a bundle calling `run()` on its restart; nothing to re-bake (#B702, #B664)
* The framework CLI's log-listener port file (`mq-listener-v<version>.port`, written by every `gina` command and read by `gina tail`) now lives under the framework home (`<GINA_HOMEDIR>/run/`, `~/.gina/run/` by default, written with mode 0600) instead of the system temp directory. Where that directory is shared between local users (`/tmp` on Linux by default), another user could create the file first: every `gina` command of the other users then failed at start-up, and on hosts without the kernel's `fs.protected_symlinks` protection a symbolic link there had the command overwrite a file of that user's choosing with the port number. Affected: every version up to 0.7.0. Pickup: restart the framework (`gina framework:restart`) and any running `gina tail`; nothing to re-bake (#B704)
* The cross-origin write guard in front of the built-in `/_gina/*` control endpoints now covers every URL those endpoints answer. Since 0.6.10 it refused a write from a page on another origin only when the URL began with `/_gina/` in lower case, while several endpoints also answer a leading segment (`/web/_gina/maintenance`, `//_gina/maintenance`), the endpoint path at the end of the query string (`/?next=/_gina/maintenance`) or another letter case (`/_GINA/cache/clear`, `/_GINA/storage/gc`). A page on another origin, visited by an operator browsing from an address listed in `app.json` `admin.allowFrom` (loopback by default), could therefore turn maintenance mode on (a 503 for every visitor), flush the render cache, run a storage garbage collection or trigger a release rebuild. The guard now looks for `/_gina/` anywhere in the URL, in any letter case; a cross-origin browser request with an unsafe method to an application URL that merely contains `/_gina/` (in its query string, for instance) is refused too, while same-origin pages and non-browser clients are unaffected. Affected: 0.6.10 through 0.7.0. Pickup: restart the bundle; nothing to re-bake (#B708)
* The admin `/_gina/*` endpoints (`/_gina/info`, `/_gina/cache/stats`, `/_gina/cache/clear`, `/_gina/storage/*`, `/_gina/release/*`, `/_gina/maintenance`) and `/_gina/metrics` no longer admit a request relayed by a reverse proxy running on the bundle's own host. They authorise a caller by network address alone (`app.json` `admin.allowFrom` and `metrics.allowFrom`, loopback by default), and a proxy on the same host connects from loopback, so every client it forwarded was admitted: anyone who could reach the site could turn maintenance mode on (a 503 for every visitor), flush the render cache, run a storage garbage collection or read the process and cache state, with no browser and no credential. Blocking `/_gina/` at the proxy did not close it either, because several of these endpoints also answered a nested path (`/_gina/health/check/_gina/maintenance`, which a proxy location for the health check forwards), the endpoint path at the end of the query string, another letter case or an empty leading segment. A loopback entry now admits a caller only when it connects directly: a request from 127.0.0.1 or ::1 that carries a forwarding header (`X-Forwarded-*`, `Forwarded`) or a Host without a port is refused with 403, and the first refusal is logged once. An address listed explicitly, such as a proxy on another host, still admits what it relays. The endpoints now match only their exact path, at the root or under the bundle's own webroot, with any query ignored; `/_gina/storage/*` and `/_gina/release/*` match in lower case only. A same-host proxy that forwards the Host header with its port and adds no forwarding header cannot be told from a direct client and is still admitted: call these endpoints on the bundle's own port from the host or the pod, and block `/_gina/` at the edge. A bundle bound directly to port 80 or 443 receives a Host without a port from every direct client; set `server.proxy.requireForwardedHeaders: true` there to keep loopback access. Affected: 0.3.14 through 0.7.0. Pickup: restart the bundle; nothing to re-bake (#B709)
* One unauthenticated GET for the client routing table spelled in another letter case, such as `/_gina/assets/Routing.json`, no longer ends a bundle on the isaac engine (the default). Its routing-table fast path tested the URL without regard to letter case, then looked the file up by the requested spelling with an exact comparison: any spelling other than `routing.json` found nothing, and reading the empty result threw an uncaught `TypeError` that ended the process, before routing and every route guard, with any path prefix. The looked-up name is now lower-cased, so every spelling the test accepts serves the table. A request the bundle classified as proxied was served the host-stripped table and escaped the crash, but that classification reads request headers that a client reaching the bundle directly sets itself. The express engine serves the table from memory and was not affected. Affected: 0.1.6 through 0.7.0. Pickup: restart the bundle; nothing to re-bake (#B707)
