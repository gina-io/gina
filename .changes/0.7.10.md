## 0.7.10 - 2026-11-06
### Added
* With `settings.json > server.logRequestStart: true`, each application request writes one info line when it arrives, before its body is read: `METHOD [>] /path [ req <id> ]`, the id being the request's correlation id (the `X-Request-Id` the answer echoes). gina otherwise logs a request when it completes, so a request that blocked the bundle (a slow body parse, middleware, action or render) appeared nowhere in its log. The path carries no query string and its control characters are written as visible escapes; in JSON log mode the line also carries `requestId` and `durationMs`. The health route, the other `/_gina/*` endpoints, static files and maintenance answers write no line, nor does a page the isaac engine's in-memory render cache serves. Off by default; only the boolean `true` turns it on, read once at boot.
### Fixed
* A staged file input's own value is no longer sent with the form's data when the input has a rule of its own and a matching `_case_` condition names it too: the known issue of 0.7.9 (#B1099). A rule of its own is one declared at the top level of the rule file under the input's name, or a top-level key written as a regular expression that matches it. Since 0.7.9 such a rule judges the files the input holds, and the value it judges (the names of those files, or an empty string) is left out of the data; in that shape it was sent. If fields of the input's files came before it in the form, that value landed in the files' list: under a top-level name such as `doc` it replaced the list, and the fields that came before it were lost; under a nested name such as `doc[files]` the list ended with that string. Every staged input is left out now, whichever rule judged it. The browser bundle carries the fix. Pickup: a re-bake.
* A page served from the render cache now answers with its own `X-Request-Id`. A hit answered with the id of the request that filled the entry, even when the request sent its own `X-Request-Id`; on the Isaac engine the hit now resolves its own id (a valid inbound one is kept, else a new one is generated), and on both engines a hit no longer replays the stored one. Pickup: a bundle restart, no re-bake (#B1100).
### Security
* A page served from the render cache no longer sends one visitor's cookies to the others. A cache entry stored every header of the response that filled it, `Set-Cookie` included, and every hit sent them back: a cookie set before the render, by a middleware (the CSRF plugin's `gina-csrf-token` included) or by the action, reached every visitor of the cached page until the entry expired, and the `fs` strategy also wrote it to the entry's `.meta` file. The session cookie of `gina.plugins.Session` was not affected (express-session adds it when the response starts, after the entry is stored). An entry now stores no `Set-Cookie` on any strategy (memory, `fs`, `redis`), and both engines' hits skip it in an entry stored by an earlier release, so a cookie set on a cached route reaches only the visitor whose request filled the entry. Pickup: a bundle restart, no re-bake (#B1101). A security advisory accompanies this fix: [GHSA-5gr9-hq8v-f4xc](https://github.com/gina-io/gina/security/advisories/GHSA-5gr9-hq8v-f4xc).
