## 0.7.11 - 2026-11-18
### Added
* With `settings.json > server.stallWatchdog: { "enabled": true }`, a worker thread watches the bundle's main thread and reports a stall while it is still happening: when the main thread's heartbeat has not moved for `threshold` (default `"5s"`, at least `1s`), the thread writes one crit line itself, `[ STALL ] main thread blocked: no heartbeat for 5.3s — frames: OrdersController.import (src/api/controllers/controller.orders.js:57:13) <- … — in flight 2: PUT /orders/42 [ req <id> ] 5.4s, …`, naming the blocked thread's call frames (on Node) and the application requests in flight, oldest first, by the `X-Request-Id` their answers echo. It writes the line to the process's stdout and, when the bundle runs under the framework daemon, through its own connection to the log relay `gina tail` reads. A blocked main thread runs none of its own logging, and an orchestrator's liveness probe may end the process before the block ends, so this line is what reaches the log. When the main thread resumes, a warn line gives the whole silence, and with app.json metrics enabled `gina_main_thread_stalls_total` and `gina_main_thread_stall_seconds` count the stall. The line is masked with the log redaction rules, and it is one JSON object in JSON log mode. Off by default: only the boolean `true` turns it on, read once at boot, and on an enabled block an unknown key or a wrong value refuses the boot. To read the frames, the thread connects to the main thread's inspector, with no `--inspect` flag, pauses it for about a millisecond and resumes it; files are named relative to the project or the framework directory. A main thread inside a native call answers nothing, so after a one-second deadline the line says `frames: none (native-call-or-outside-js)`; a debugger already holding the thread paused is left alone (`frames: none (debugger)`); on Bun the line says `frames: none (bun)`. `captureFrames: false` leaves the frames out, `frames` (1 to 32, default 8) sets how many are named and `inFlight` (1 to 64, default 8) how many requests. Works on Node and Bun.
* An opt-in load limit for popins, `loadTimeout`, in milliseconds: per popin with `new Popin({ name, loadTimeout: 15000 })`, or for every popin without its own value with `gina.setOptions({ popin: { loadTimeout: 15000 } })`; a popin's own `0` means no limit for it. A popin whose content request never answered kept its loading shell, and its trigger stayed busy, for as long as the request hung. With a limit, a load still unanswered at it is aborted and fails like any failed load: `error` fires with `{ status: 408, error: 'Request Timeout' }`, then the shell closes unless a listener loaded content, and the trigger is released. A close during the load still cancels it without an `error`. A hover or focus warm of the URL carries the same limit, so a click that adopted a stalled warm fails at most twice the limit after the warm began. There is no limit unless one is set. The popin plugin ships in the browser bundle: run `gina bundle:build` to pick it up. (#B1108)
* A bundle now warns once at boot, in one `[CONFIG][loadBundleConfig]` line, about each route whose `param` block binds a URL placeholder under a key gina reads as configuration, such as `"section": ":section"`. The presence of a key in `param` is what binds a URL segment, but `req.routing.param` keeps the placeholder text for every key the matcher does not fill, so gina reads `":section"` as `page.section`, `":code"` as the redirect status and `":isPopinContext"` as false. The warning covers the 24 keys gina reads as configuration: `requireAuth`, `public`, `roles`, `policy`, `dto`, `responseDto`, `messageValidator`, `lane`, `wsHandler` and `wsOptions` (a placeholder there already stops the boot), `control`, `route`, `url`, `urlIndex`, `ext`, `project`, `hostname`, `port` and `method` (it fails per request), and `ignoreWebRoot`, `section`, `isPopinContext`, `keep-params` and `code` (a wrong value, with no error). It names the binding whatever the route does, so a route that binds `code` and never redirects is warned too. `path`, `namespace`, `title` and `file`, which gina fills from the URL, and `culture`, which a `culturePrefix` route reads from the URL, are not warned. Bind the segment under another name (`"url": "/item/:itemCode"` with `"itemCode": ":itemCode"`); nothing is rewritten. Pick it up with a bundle restart. (#B1124)
### Changed
* A staged file input now refuses, before any request is sent, a chosen or dropped file of a type its `accept` attribute excludes, or larger than its new `data-gina-form-upload-max-size` attribute. Until now the browser's file dialog only filtered what it showed (a user could still choose « All files »), a drop was not filtered at all, and every file was sent to the staging route; the server was the only check, and it stays the authority. `accept` is read as the browser reads it: comma-separated tokens, trimmed and case-insensitive; `.ext` matches the end of the file name, `type/*` the start of its type (`*/*` any file, one with no type included), any other `type/subtype` the type exactly, and a file the browser gives no type matches an extension token or `*/*` only. A token of another shape (`jpg`, a type with parameters) is ignored, with a warning in dev mode. `data-gina-form-upload-max-size` reads as `upload.maxFieldsSize` does: a number with an optional `b`, `kb`/`k`, `mb`/`m` or `gb`/`g` (1024-based), a bare number in megabytes, `0` or an empty value for no limit; a value that does not parse checks no size, with a warning in dev mode. A selection holding one refused file is refused whole: nothing of it is staged, the files the input already held keep their previews, links and hidden fields, and a staging of its earlier selection still in flight finishes. The input's error element shows « photo.png was not uploaded: this type of file is not accepted » or « scan.pdf was not uploaded: the file is too large », one line per reason (two new strings, `uploadTypeRefused` and `uploadSizeRefused`, translatable through `gina.config.a11y`), the form's live region announces them, and the input's `data-gina-form-upload-on-error` callback runs with `{ refused: true, reason, files, error, transportError: false }`, where `reason` is `'type'` when a file was refused for its type, else `'size'`, and `files` names every refused file. A staged input whose `accept` names fewer types than its upload group allows now refuses the files of the other types: list them in `accept`, or remove it.
* Locking @rhinostone/swig 2.12.4 in both lockfiles (both manifests keep ^2.12.1, so a fresh install already resolves 2.12.4 or later): in a gina process, a template's read of `count` or `functionCount`, gina's own Object.prototype helpers, now reads only an object's own key, so `{{ r.count() }}` renders an empty string where it rendered the number of keys, and `{% if r.count %}` is false for an object without its own `count` key, where it was true (a query row's `count` column reads as before); a template's `{{ _ext.name }}` renders an empty string, while a custom tag's compiled code still reads `_ext`; a context key named like a JavaScript global (`JSON`, `Math`, `encodeURIComponent`) that holds null or undefined now hides that global. swig 2.12.4's own notes list its other read changes. Server-side only: a bundle restart picks it up, no re-bake. (#B1138)
### Fixed
* A rule that a `_case_` condition gives a staged file input now judges the files the input holds (#B1095). With one `_case_` key the rule was never applied, so a required staged input refused nothing; with two or more, the condition of a driver that is not the last one judged the input's own value, so an edit form showing a saved file was refused, and a file that had just been staged passed on the browser's placeholder. The submit control also follows the input's files when the form's rules hold a `_case_` key. A top-level rule key written as a regular expression that matches the input's name was already a rule of its own, which judges the files since 0.7.9. The browser bundle carries the fix. Pickup: a re-bake.
* A staged file input that has no `data-gina-form-upload-action`, on a page without an `upload-to-tmp-xml` route to fall back on, now refuses a chosen or dropped file before any request is sent (#B1094). The file used to be posted to `/null`, and the 404 that answered was reported as a failed staging. Now the input's error element shows « photo.png was not uploaded » (a new `uploadNotSent` string, translatable through `gina.config.a11y`), the form's live region announces it, and the input's `data-gina-form-upload-on-error` callback runs with `{ refused: true, reason: 'action', files, error, transportError: false }`. The input is emptied once its `change` event is over, and the files it already held keep their previews, links and hidden fields. In dev mode a console error names the missing attribute.
* Popins loaded with `gina.popin.load(name, url)` and no options, or with one options object passed to several loads, no longer share one options object. Before, the second popin loaded that way took the first one's `preOpen` (it showed the first popin's loading shell), `loadingShell` and class, and the options object passed gained the popin's options. `load()` now copies the options it is given and leaves the caller's object as it was. A load without options to another site also no longer stops later popin loads to a sibling subdomain from sending credentials. Popins opened by their `data-gina-dialog` triggers were not affected. The popin plugin ships in the browser bundle: run `gina bundle:build` to pick it up. (#B1109)
* `self.downloadFromURL(url, { file })` now answers a 500 through `throwError()` when `options.file` has no extension of ASCII word characters (`report`, `notes.été`, `a.pdf ` with a trailing space) or is not a string, as it already did for a url without such an extension. `options.file` replaced the url's name after that check, so such a name made the method throw a TypeError inside its promise: the request got no response, and a call that was neither awaited nor caught raised an unhandled rejection. A valid `options.file` is unchanged. (#B1111)
* `self.downloadFromURL(url)` now answers a 500 through `throwError()` when `url` is not a string, and accepts only the `http` and `https` schemes. A url that was `undefined`, `null` or a number made the method throw inside its promise, so the request got no response; a scheme such as `httpfoo` passed the old check and the method rejected with « Cannot find module », also with no response, and `http2` loaded Node's http2 module before failing. Such schemes now get the « Scheme not supported » 500 that `ftp` already got. (#B1114)
* A download name holding a Latin-1 letter (`résumé.pdf`, `Accusé de réception.pdf`) is now sent by `self.downloadFromLocal()`, `self.downloadFromURL()` and `self.serveFromStorage()` (on its in-process path; on the `s3` offload path, #B1115 signs the same value) with an RFC 8187 `filename*=UTF-8''…` parameter after an all-ASCII `filename` fallback (`resume.pdf`). Such a name was sent as raw bytes in `filename="…"`, which Chromium and WebKit decode as UTF-8, so the browser saved the file with U+FFFD in place of each accented letter. The fallback drops accents and writes `?` for any other non-ASCII character, so a client that reads only `filename` (`curl -OJ`) saves `resume.pdf`; a name above U+00FF now gets the same fallback, and a printable ASCII name keeps the header it had. (#B1113)
* `self.downloadFromURL(url, options)` now answers a 500 through `throwError()` when `options` is a string, a number, a boolean or another primitive. Such a value made the method throw inside its promise, so the request got no response. `null` downloads with the defaults, as before, and a function in that position, as in `self.downloadFromURL(url, cb)`, is copied like an object: nothing is written onto it, and the download goes ahead as before. (#B1118)
* `self.downloadFromURL(url, options)` no longer writes into the `options` object it is given. It merged its defaults into that object, then wrote the formatted `Content-Disposition` and the forwarded headers (`content-type`, `x-request-id`) into it, so one object passed to two calls, such as an options object kept at module level, sent the second download under the first one's filename and forwarded the first request's `x-request-id` upstream. The method now works on a copy of the object and of its `headers`; every other value it holds (an `http.Agent`, TLS buffers, a `lookup` function, an `AbortSignal`) is passed on as it is. (#B1112)
* `self.downloadFromURL(url)` now sends an `https` url that names no port, such as `https://example.com/brand/logo.png`, to port 443. Its defaults carried `port: 80`, so such a url opened TLS on port 80 and the download answered 500. A port in the url or in `options.port` is used as before, and an `http` url without one still goes to port 80. (#B1119)
* `self.downloadFromURL(url)` no longer answers a 500 when the url's host is that of a bundle named in `app.json`'s `proxy` (a `bundle@project` hostname) and the url's port differs from that bundle's. The override meant to send such a request to the bundle's port replaced the host with the port number instead, so the request was never made. The request now goes to the bundle's port. (#B1120)
* `self.downloadFromURL(url)` now reads the host and the port from the url's authority only: what follows `scheme://` up to the first `/`, `?` or `#`. A `:<digits>/` anywhere in the url, such as a path segment in `/files/a:1/x.pdf` or a query holding another url with a port, used to set the port, so the request went to that port. A `user:password@` stayed in the host and an IPv6 literal lost part of its address (`[::1]` became `[:]`), so neither request could reach its host. An IPv6 literal now reaches Node without its brackets, and a url carrying credentials answers 500 and names `options.auth`, where they go. The path goes out as written. (#B1121)
* `self.redirect()` no longer fails on a route whose `param` block binds a URL segment under the name `code` (`"code": ":code"`). The redirect status is read from `param.code`, which keeps a binding's placeholder text, so every redirect reading that route sent the status `:code`: over HTTP/1.1 the request answered 500, over HTTP/2 it answered 200 with the redirect's JSON as the page. `param.code` now sets the status only when it is 301, 302, 303, 307 or 308 (`302` and `"302"` alike); any other value, which was sent as it was, answers 301, the documented default, and is logged once per route and value. (#B1122)
* `self.requireController(namespace)` called without its `options` argument (or with `null`) now builds the controller with the options of the request being served, the object an action passes as `self._options`. It used to throw `TypeError: Cannot read properties of undefined (reading 'controlRequired')` before doing anything, although the argument is documented as optional. A route middleware and a bundle's `controllers/setup.js` have no `self._options` of their own, so in them the method threw however it was called; it now works there too. A call that passes options is unchanged. (#B1031)
* On the `s3` storage adapter, a download served through the offload path (`self.serveFromStorage()` with `download` or `filename`, or the driver's own `resolve()` with them) now signs the `Content-Disposition` value the in-process path sends: a name of printable ASCII keeps its quoted `filename`, and any other name gets an all-ASCII `filename` fallback (`resume.pdf`), then `filename*=UTF-8''…`. The presigned `response-content-disposition` carried the name raw, and the provider copies it into its response header: AWS S3 sent a Latin-1 name such as `résumé.pdf` back re-encoded as ISO-8859-1, which Chromium and WebKit save with U+FFFD in place of each accented letter, and refused any name with a character above U+00FF (`l’offre.pdf`, a CJK or emoji name) with `400 InvalidArgument`, so the download failed after the redirect; MinIO sent the name back unchanged. `offload: false` avoided it. (#B1115)
* A gina page loaded in a same-origin frame now starts its own client instead of taking over the parent page's. Up to 0.7.10 the client merged the parent frame's `gina` instance into the frame's at start-up, and the parent's values won: the frame's loader stopped at once, so its own configuration, session and forms were never applied, its popin, validator and navigation were not started, and `new Popin()` in the frame looked for the parent's popin container in the frame's document and threw `Cannot read properties of undefined (reading 'addListener')`. Every document now has its own instance and the client no longer reads its parent frame at all, so a cross-origin parent (0.6.28) cannot interrupt the start-up either. Code in a frame that read its parent's values through its own `gina` now reads its own; read `parent.gina` where the two pages share an origin. The client ships in the browser bundle: run `gina bundle:build` to pick it up. (#B1130, gh#103)
* `self.redirect('<route>')`, a route name without `@bundle`, now redirects to that route of the current bundle, as the method's documentation and the controller guide describe. It looked the route up as `<webroot characters>-<route>`, a name gina never creates: under the default webroot `/` the method threw and the request answered 500, under any other webroot it answered 404. Route names are now lowercased in both forms, as `lib.routing.getRoute()` resolves them, so `self.redirect('Home@frontend')` no longer answers 404 either. (#B1125)
* On a route with `culturePrefix: true`, `req.culture` now takes the URL value of the segment bound to `param.culture`, as the i18n guide describes: `GET /fr/dashboard/42` gives `fr`, also when a cookie or `Accept-Language` asks for another culture. The negotiator read `req.routing.param.culture`, the route's configuration, where a binding such as `"culture": ":culture"` keeps its placeholder text, so the URL step never matched a catalog and the request took its culture from the cookie, `Accept-Language` or the bundle default. A literal `param.culture` is used as before. Bind the culture segment in `param`: a `:culture` segment left out of it makes the route match nothing. (#B1123)
* A route in `routing.json` with no `param` block, or with `"param": null`, now stops the bundle's boot with an error that names it, « [<rule>@<bundle>] Bad routing syntax: the route has no `param` block; `param.control` is required », written to stderr before the process exits with code 1. The boot used to stop on an uncaught « TypeError: Cannot read properties of undefined (reading 'control') » that named neither the route nor the block. `param.control` is required (the routing guide's Route fields): add the block to the route. A route that has no `param` block but a non-empty `hostname`, and a `param` block without `control`, boot as before. (#B1133)
* A `routing.json` redirect route that names its target in `param.route`, `{ "control": "redirect", "route": "<route>" }`, now resolves that name as `self.redirect('<route>')` does: a name without `@bundle` names a route of the current bundle, the name is lowercased, and `<route>@<bundle>/<env>` is accepted. The name was looked up as written, so only `"<route in lowercase>@<bundle>"` worked: a bare name, a name with capitals or one with an env suffix answered 404. A target in another bundle (`"<route>@<other bundle>"`) now redirects to that bundle's hostname, as the string form does; it got a relative `Location` on the current host. Pick it up with a bundle restart. (#B1134)
* `lib.routing.getRoute()` now looks for a fixed `param` value as written when it decides which values go into the query string of a GET route, as the routing guide describes. A fixed value was read as a regular expression: a value holding a regex metacharacter, such as `"label": "C++"`, `"(beta"` or `":-)"`, made `getRoute()` throw a `SyntaxError` for that route whenever it was called with params, and `"a.c"` matched the URL `/abc/` by accident, which could leave a value passed to `getRoute()` out of the query string. The keys gina reserves (`title`, `file`, `namespace`, `path`) were never read this way. `lib/routing` is in the browser bundle: pick it up with a bundle restart and a re-bake. (#B1135)
* Under a non-root webroot, a `routing.json` redirect route that sets `param.path` now redirects to that path under the webroot: with the webroot `/web/`, `"path": "/general"` and `"path": "general"` answer `/web/general`, and `"path": "/"` answers `/web/`. The path only lost its first character, so the `Location` was relative (`general`, `eneral`, or empty) and the browser resolved it against the request URL. A custom action that calls `self.redirect(req, res, next)` on a route with `param.path` gets the same. Every other reader gets `param.path` as written, where it got it without its first character: a page route whose `param.path` names its template file, and an action that reads `param.path`. `ignoreWebRoot`, a `route` target and an absolute URL are unchanged; a route that relied on the relative `Location` can set `ignoreWebRoot: true` with the full path, which answers the same before and after. Pick it up with a bundle restart. (#B1137)
### Security
* `self.requireController()` no longer keeps a copy of the required controller on every call outside development. Its cache guard had been commented out since 0.1.0, so each call evicted the super controller and the required controller from the require cache and required them again, and every copy stayed referenced by the router module for the life of the process: memory grew by about the required controller's source size per call once V8 had flushed its code, until the process ran out of memory. Every call that passed an options object was affected, as an action's `self.requireController(namespace, self._options)` does, and so was `resumeRequest()` when it replays a non-GET request into another namespace (a call without options threw before reaching the require cache, #B1031), so a route reachable without authentication let a client exhaust the process's memory by repeating requests. Outside development both modules now load once per process, as a routed controller's do, so a required controller's module-level code runs once rather than on every call; in development they are still required again on every call, and the old copies are now released. (#B1126)
* On the isaac engine, an `X-Forwarded-Prefix` request header whose value opens with two slashes is now refused like a malformed one, and the page keeps the bundle's own webroot. Such a value passed the path-character check added in 0.6.8, but the public webroot composed from it (`//evil.example/<webroot>/`) is a protocol-relative URL: the browser fetched the client routing table (`_gina/assets/routing.json`) from the host it names, and the gina stylesheet too when `gina.min.css` was not already linked, and the client then built its route URLs from the table that host served. A client reaching the bundle directly, or through a proxy that passes the header on (nginx does unless its configuration sets `X-Forwarded-Prefix`), could send such a value; with the concurrent-render and render-cache defects fixed in the same release (the second is #B1131), it could reach other clients' pages. (#B1129)
* With the render cache off, the default when `settings.json` has no `server.cache` block, in production as in development, concurrent renders of swig pages sharing a layout no longer serve one another's request values. Every such render wrote the layout to one shared file under `templates/html/.gina-layout-cache/`, wrote the request's whispered values into it (`page.environment.hostname`, `.webroot`, `.culture`, the validation labels, the proxy host), and swig compiled the page from that file, so under parallel load a page could carry another request's hostname, webroot or culture, or arrive without gina's client loader, and on a bind-mounted templates directory the file could be found absent (`ENOENT`, a 500). Those values come from request headers (`X-Forwarded-Host`, `X-Forwarded-Prefix`, `Accept-Language`, the culture cookie), so one client's headers could reach other clients' pages. Each render now assembles its layout in memory and swig compiles the page against it through the engine's loader; with the cache off nothing is written under `.gina-layout-cache`, and with the cache on the file is still written, now without the values that vary per request (#B1131). (#B1129)
* With the render cache on (`server.cache.enable`), the first page render no longer fixes the values a swig page's client loader reads for each request, for every later visitor. Those values (the public hostname and webroot, built from `X-Forwarded-Host` and `X-Forwarded-Prefix`, the proxy host, the negotiated culture and its validation labels) and a layout's `{{ page.section }}` were written into the layout before swig compiled it, and with the cache on each view's compiled template is kept and the layout is written under `templates/html/.gina-layout-cache/` and read back by every later compile, a restarted process included. So the first page render after that file was created (after a deploy that starts without it, or after the directory was emptied) gave its hostname, webroot and culture to every later render of every view sharing the layout, until the file was removed: a client reaching that render first with forwarded headers of its own fixed a foreign webroot or hostname for everyone, and a route's output cache replayed the page. Swig now renders these values from each request's data; every other value is written into the layout as before, and the http/2 preload hints still resolve a layout URL written with `{{ page.environment.webroot }}`. A layout file an earlier release wrote is primed again on the next compile. Pages a route's `fs` or `redis` output cache stored before the upgrade are not served after it, since that cache is namespaced by framework version, unless `GINA_CACHE_NAMESPACE` keeps its value across the upgrade: then run `gina cache:clear`. The output cache still keys a page on its URL alone, so a cached page keeps the host and culture of the request that filled it until it expires. (#B1131)
