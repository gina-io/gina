## 0.7.13 - 2026-11-22
### Added
* A bundle warns once at boot, in one `[CONFIG][loadBundleConfig]` line, about each route URL segment that holds two or more placeholders (`/range/:from-:to`, `/shop/item-:sku-:lang`), whatever the route's method: gina never matches such a segment against a value, and a request matches it only by carrying its text as written. Give each placeholder a segment of its own (`/range/:from/:to`). The two boot warnings added in 0.7.12 no longer list such a segment. Nothing is rewritten (#B692).
### Changed
* On a `DELETE` route with `requirements`, a placeholder with no requirement matches only when the route binds it in `param`, as on `GET`. From 0.7.6 to 0.7.12 such a route answered where its `GET` twin answers 404, and the unbound placeholder reached `req.delete`. Bind the placeholder (`"grp": ":grp"`) to keep the route matching (#B1144).
* On a `DELETE` route with `requirements`, a placeholder's name is its letters, digits and underscores, as on every other route, and its value is the whole segment: `/feed/:id.json` binds `id` and its requirement on `id` tests `42.json`. From 0.7.6 to 0.7.12 that route bound `id.json`, skipped the requirement and matched any segment. An action that read `req.params['id.json']` or `req.delete['id.json']` binds `"id": ":id"` and reads `id` now. The 0.7.12 boot warning for such a placeholder no longer names a `DELETE` exception (#B1149).
* A WebSocket route reads a placeholder's name as an HTTP route does, its letters, digits and underscores: `/live/:lang-code` exposes `request.params.lang`, holding the whole segment, instead of `request.params['lang-code']`. A segment with no name after its `:`, or with two or more placeholders, is compared as written (#B1151).
* On a `DELETE` route with `requirements`, a URL segment that starts with a placeholder and holds two or more (`/range/:from-:to`) matches a request only when the request carries its text as written, as on every other route. From 0.7.6 to 0.7.12 that route matched any non-empty segment there and wrote it under the rest of the segment's text (`req.delete['from-:to']`); the router now tries the next route. Give each placeholder a segment of its own (`/range/:from/:to`) (#B692).
* On a `DELETE` route with `requirements`, a placeholder with a regular-expression requirement matches only when the route binds it in `param`, as on `GET`. Up to 0.7.12 the requirement alone let such a route answer where its `GET` twin answers 404, and the value reached `req.delete` only, never `req.params`. Bind the placeholder (`"id": ":id"`) to keep the route matching (#B1155).
### Fixed
* The navigation module (`gina/nav`) reads placeholder names as the server does. For `/:lang-code/x/:id` on a route binding `lang-code`, it compiled the segment under the name `lang-code`, where the server reads `:lang` holding the whole segment and refuses the request, so the module intercepted links the server refuses. It now leaves such a variant uncompiled, as it already did for `/page:number`, and no longer intercepts links through that route. The routing map served to the browser is unchanged. Re-bake the bundles to pick it up (#B1150).
* A route URL segment holding a `:` with no name after it (`/t/12:`), or one that is not a valid regular expression (`/r/:id)`, `/r/[:id`), no longer answers 500 « Rule [ … ] needs your attention » on every request that reaches it, which also kept every later rule from being tried. A nameless `:` matches only a request carrying the segment as written; the other segment is read like any segment holding one placeholder, and the `path`, `namespace` and `title` rewrites replace the segment's own text literally (#B1146, #B1148).
* `getRoute()` no longer warns « placeholder not defined » for a value holding `host:port/`, such as a redirect target, and now warns for an unfilled placeholder named `d`: its port check read a literal `d` where a digit was meant (#B1152).
* A `validator::` requirement that the route does not bind in `param` reads the URL's placeholder names in any letter case: `:userId` was read as `:user`, so a `query.data` entry referencing `":userId"` was dropped before the validator ran, and, when the validator declared a `query.data` entry, a URL whose every placeholder name starts with a capital (`/u/:ID`) answered 500. The same block read `:lang-code` whole and set `req.params['id.json']` for `:id.json`; it now reads `:lang` and sets `req.params.id` (#B1153).
* When a route's matcher throws, the request is answered once: its 500 « Rule [ … ] needs your attention » is no longer followed by a second error line for the same request, with an error reference of its own: « Page not found », or the 405's when an earlier rule had refused the request's method (#B1154).
* A route whose URL segment holds two or more placeholders and that declares `requirements` no longer answers 500 « Rule [ … ] needs your attention » to a request carrying a decodable escape (`/shop/item-1%202-fr`), which also kept every later rule from being tried: the segment does not match, and the next rule is tried (#B692).
* On Node.js 22.21.0, an HTTP/1.1 request carrying `Upgrade` headers to an `https` HTTP/2 bundle no longer stops the bundle. That release's HTTP layer calls the server's `shouldUpgradeCallback`, which its `http2` server with `allowHTTP1` (the default) never defines, so the request threw inside Node's parser (nodejs/node#60336, fixed in Node.js 22.21.1). gina now gives such a server Node.js 22.21.1's own callback at listen(); other Node.js releases and Bun are unchanged (#B1147).
* Client navigation: a route whose URL the navigation module cannot match exactly (text next to a placeholder in a segment, like `/page:number`, or a placeholder name holding a character other than a letter, a digit or an underscore, like `:lang-code`) now stops the scan when the server could answer the link from it. Before, the module skipped such a route, so a later `negotiate: true` route took the link: one wasted fragment request, an `error` event, then a full page load. Such links now navigate normally, as the client navigation guide says, and `gina.nav.matchUrl()` answers `null` for them (#B1156).
* Storage: put() and writeSegment() refuse a source stream that has already ended or been destroyed, with an error whose code is STORAGE_STREAM_SPENT, before anything opens. Handed such a source (most often an action's req, whose body gina has already read), put() stored an empty object and reported success under the sharded, stream and cas strategies, or never called back (sharded with size tiering on), and writeSegment() answered length 0 with no error, or never called back and kept the session data file open (a destroyed source). The s3 adapter's put() runs the same check. The code comments whose examples passed req now pass a stream of the uploaded file (#B1060).
