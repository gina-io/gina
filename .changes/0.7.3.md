## 0.7.3 - 2026-10-05
### Fixed
* A `GINA_VERSION` that names no installed framework version is now refused before the command runs, whether it was exported or set with `--version=<v>`: the CLI exits 1 with a message naming the path it expected and, for a version number, the `env -u GINA_VERSION gina framework:add <version>` command that installs it side by side. Before, only the installed package's own version was checked, so an exported `GINA_VERSION=latest` (or `--version=latest`, or a version number that is not installed) went on to migrate `~/.gina` to that phantom version (a `latest` entry in `main.json` and `gina.db`, an empty `~/.gina/latest/` directory, `gina version` printing `vlatest`) and the command carried on. A version installed side by side with `framework:add` is accepted as before. A `--<name>=<value>` argument also keeps its value exactly as given: when the flag name had no hyphen of its own, the value's first hyphen was turned into `_`, so `--version=0.7.2-alpha.2` arrived as `0.7.2_alpha.2`. Entries an earlier run already wrote are not removed. Takes effect on the next `gina` command. (#B584)
* `gina start` (and `gina framework:start`) now exits non-zero when the framework stops before it is ready: with the framework's own exit code, with 1 when that code was 0, or with 128 plus the signal number when a signal stopped it (137 for SIGKILL). It used to exit 0, so a script that tests the exit code read success on a refused `GINA_VERSION` or an error while the framework boots, and a framework killed by a signal made the command crash with a TypeError instead. A start that reaches the ready line, or finds the framework already running, still exits 0. (#B759)
* A warning on standard error, such as a deprecation notice, no longer aborts `gina start`. The command exited 1 as soon as the framework printed a line containing "warning" before it was ready, and the framework, cut off from its output, then stopped, so the start failed. The warning is now printed and the start carries on; a debugger line or "address already in use" still ends it with exit 1. (#B760)
* A staged upload's `send()` no longer reads the event being dispatched when it runs. The upload group now comes from the file input the virtual upload form stages for, so `gina.validator.$forms[<virtual form id>].send(formData)` called outside that input's change event stages the file in the input's group: outside any event it used to fail with a TypeError while the request still went out with no multipart boundary and no group, and inside an unrelated event it took that event's element's group. A `send()` with no data now sends an empty body instead of throwing and leaving the form marked as sending. Selecting or dropping a file was not affected. (#B758)
* After a client navigation (`data-gina-nav`) that closes an open popin, focus now lands on the swapped region and the page keeps the navigation's scroll position, as after any other swap. The popin used to be closed after the region was focused, so closing it returned focus to the popin's trigger and scrolled the page back to it, with modal and non-modal popins alike. (#B762)
* `gina start` no longer reports another program on the framework port as a running framework. When the port was already in use, it trusted any `~/.gina/procs.json` entry for it without checking: a port held by another program read « already running » (with « PID `null` » when no entry named the port), a stale entry left by a stopped framework was reported as running under a dead pid, and both exited 0 while a half-started framework kept the MQ port busy; any other error opening the port, such as EACCES, made `gina start` hang. « Already running » now needs a recorded pid that is a running gina framework, on Node or Bun. Otherwise the start prints the cause, the fix (`gina framework:set --port=<port>`) and, outside Windows, an `lsof` command that finds the program holding the port, then exits 1 and releases the MQ port; any other error opening the port exits 1 with that error. (#B761)
* A URL both declared in `templates.json` and written in the layout now appears once in the `link` header of an HTML page, instead of twice. (#B767)
* The stylesheets (`<link rel="stylesheet">`) and scripts (`<script src>`) written in a layout are now hinted in the `link` header of an HTML page, with `as=style` and `as=script`; they never got an `as`, so they were never hinted. A tag the browser could not match a preload to is left out: one carrying `integrity` or `crossorigin`, a stylesheet whose `media` is not `all` or `screen`, an alternate stylesheet, or a `type="module"` or `nomodule` script. (#B766)
* The automatic preload hints of an `http/2.0` bundle in production, the 103 Early Hints and the `link` header of the 200, are now limited to `templates.json > preloadHintsMaxSize` bytes, 1,024 by default (`0` = no limit), keeping their entries in order and stopping at the last one that fits; `preloadHintsEnabled: false` sends neither. Both keys can be set in `_common` or in a page's own entry. The hints had no limit, so behind a proxy with a small response-header buffer (nginx's `proxy_buffer_size` is one memory page, 4 KiB on most Linux hosts) a page that declared many stylesheets and scripts, or whose layout held many images, was answered 502 « upstream sent too big header ». This is a behaviour change: such pages now send fewer hints, and the assets left out still load once the browser reads the page. Raise the limit only when every proxy in front of the bundle has room for it. (#B765)
* `self.setEarlyHints([a, b])` now sends both entries over HTTP/1.1 (when `server.earlyHintsOverHTTP1` is `true`). It joined the entries with `, ` into one string, which Node.js checks as a single link value and refused, so an explicit hint with several entries was silently never sent over HTTP/1.1; each entry is now handed to Node.js separately. An entry whose parameter holds a space, such as an `imagesrcset`, is still refused by Node.js and drops that 103. (#B770)
* An `http/2.0` bundle in production no longer sends 103 Early Hints over HTTP/1.1 unless `settings.json > server.earlyHintsOverHTTP1` is `true`. Since 0.6.28 it sent its automatic 103 over HTTP/1.1 too, where it reaches a reverse proxy rather than a browser (browsers act on a 103 only over HTTP/2 and HTTP/3), and nginx older than 1.29, the versions Ubuntu 22.04 and 24.04 and Debian 12 package, takes an upstream 103 for the final response: every HTML page behind it failed (in Chromium: `ERR_HTTP2_PROTOCOL_ERROR`). This is a behaviour change, and it applies to `self.setEarlyHints()` too: a browser connected to the bundle over HTTP/2 gets its 103 as before, and behind a proxy that talks HTTP/1.1 to the bundle the 103 now stops. Turn the key on only behind a proxy that passes 103 responses on (nginx 1.29 or later with `early_hints`, Apache). (#B771)
* A page entry in `templates.json` that sets a `_common` switch to `false` (`assetVersioningEnabled`, `preloadHintsEnabled`, …) now keeps it: it used to get `_common`'s `true` back. For `javascriptsDeferEnabled`, such a page's scripts now go before `</body>` without `defer`, as documented, instead of in `<head>` with it. (#B772)
* More of the assets written in a layout get a preload hint in the `link` header of an `http/2.0` page's 200. The layout was read one source line at a time, keeping the last URL on the line, so tags sharing a line were read as one: `<img src="a.png"><script src="b.js"></script>` preloaded the script as an image and left the image out, a stylesheet followed by an image on one line lost both, a one-line `<picture>` lost its `<img>` and gave its `<source>`'s `srcset` to the next image, and a minified layout got no hint at all. Each tag is now read on its own, a start tag written over several lines included; the hints stay within `preloadHintsMaxSize`. (#B768)
* Under a webroot other than `/`, an asset URL written in a layout with the webroot, such as `{{ page.environment.webroot }}img/logo.png`, now gets its preload hint, behind a path-prefixing proxy too. Such a URL never matched a file, so it got no hint, and a stylesheet linked that way was never read for its `url()` references. (#B769)
* The `ginaEnabled` key is removed from the framework's `templates.json` baseline. It never had any effect, although the `templates.json` reference said that `false` keeps gina's CSS and JS out of a page and hides the dev toolbar; a bundle that sets it keeps working, the key being ignored as before. To hide the dev status bar on a page, render it with `self.render(data, false)`; to keep gina's own CSS and JS out of a page, set its `javascriptsExcluded` and `stylesheetsExcluded` to `"**"`, which leaves out `_common`'s stylesheets and scripts too. (#B773)
* A page no longer answers 500 on an `http/2.0` bundle, in dev and in production, when its layout links a stylesheet by hand whose CSS holds an unquoted `url(#id)`, such as the SVG reference in `fill: url(#grad)`, or a `url()` with no dot in its path. The scan that lists the `url()` references of a layout's stylesheets for the Inspector threw on them; it now skips what it cannot read. (#B774)
* A page no longer answers 500 on an `http/2.0` bundle when the first asset of its layout is an `<img>` with a `srcset` and no `src`. The layout scan kept the previous tag's URL, so such a tag first in a layout threw, and a later one overwrote the previous image's entry; a tag with no `src` or `href` now gets no hint and leaves the other entries alone. (#B775)
* A layout image keeps its preload hint when one of the layout's stylesheets names the same file in a CSS `url()`: the stylesheet's reference replaced the image's entry, the one that carries the hint. (#B776)
* A bundle installed under a directory whose name holds `404` now gets its layout preload hints, as does an asset named like `error-404.png`: the layout scan took any file path holding `404` for a missing file. (#B777)
