## 0.7.6 - 2026-10-27
### Added
* Templates can read the project's own package version as `page.environment.packageVersion`: the `version` field of the project's `package.json`, read once per process. The field is not set when the project has no `package.json` or no `version` in it, so `{% if page.environment.packageVersion %}` guards a version badge. It is not `${projectVersion}`, which in configuration files is the version in the gina manifest. Restart your bundles (#TPL3).
### Changed
* A URL placeholder's value now wins over a query-string or body key of the same name, on every request. On a route `/items/:grp/:id` that receives `?id=99` or `{ "id": "99" }`, `req.get.id`, `req.head.id`, `req.put.id`, `req.patch.id`, `req.post.id` and `req.delete.id` now hold the URL value, as `req.params.id` does. Before, the first request to a method and path took the URL value on GET, HEAD, PUT and PATCH and every later request took the client's value (#B957); a POST always took the client's value, and so did a DELETE unless a regex requirement covered the placeholder (#B954). The client's value stays readable in `req.originalUrl` on a GET, in `req.query` on a DELETE and in `req.rawBody` on a POST, PUT or PATCH. A URL segment `true`, `on` or `false` now reaches the action as a boolean on every request, where it did on the first request only, and on a DELETE only without a query string. `req.body` is now the same object as `req.post`, `req.put` or `req.patch` on the first request to a route too, as documented; it held the client's keys only there. A top-level JSON array body keeps `req.body` the array on a POST or PATCH (#B953) and an object keyed by index on a PUT. Restart your bundles (#B954, #B957).
* The boot-time sweep of staged upload parts (armed by `upload.autoTmpCleanupTimeout`) now removes a part once its mtime is older than the timeout plus one hour; it was the timeout floored at one hour. With a timeout of an hour or more the sweep acted at the moment the owning process's own timer would, as read on the sweeping node's clock, so on a staging directory shared between nodes a clock running ahead of the file's, or an attribute cache serving an older mtime, could remove a part before its owner's timer would. The extra hour absorbs that; parts a restart stranded wait one hour longer. Restart your bundles (#B472).
* A `self.query()` call to an HTTP/2 upstream that reaches its `requestTimeout` now fails with `TIMEOUT` at that moment and is never sent again. Before, the timeout destroyed the session and sent a safe method (or a call with `retryUnsafe: true`) up to twice more: a slow but live upstream ran the same action three times while the caller waited three timeouts and half a second, every other request in flight on that session failed with a 500 that carried no error code, and an attempt waiting on a session that never connected raised an uncaught `ERR_HTTP2_STREAM_CANCEL`. Now, on a connected session, only the timed-out request is cancelled. A connected session is kept, and the next call checks it with a PING before using it; a session that never finished connecting is dropped, the next call opens a new one, and the calls that were waiting on it, never sent, are sent again on a new session (#B981). A call that a second attempt used to save now fails with `TIMEOUT`: an upstream that answers slowly once (a cache warming up), a connection lost during the call when `requestTimeout` is under about 8 seconds (the next call recovers), and a call with `retryUnsafe: true`. Each timeout sends an `RST_STREAM`, which the upstream counts: more than `http2Options.maxStreamResetsPerSecond` timeouts (200 by default) within one second on one session make an Isaac upstream close that session with a warning, and an upstream running on Node.js also closes it at a sustained rate above 33 per second, once the runtime budget of 1,000 resets is spent (the `streamResetBurst` / `streamResetRate` defaults of Node.js, which an Isaac upstream changes only when its `http2Options` sets both). The calls still in flight on a closed session are retried as after any `GOAWAY` (a safe method, or `retryUnsafe`); raise the limits on the upstream, or set `server.query.http2SessionPool` on the caller. HTTP/1.1 calls are unchanged. Server-side only: a running bundle picks this up at its next restart. (#B967, #B628, #B970)
### Fixed
* On a `DELETE` route whose regex `requirements` cover its URL placeholders, `req.params` now carries the URL values (`req.params.id` on `"url": "/items/:id"` with `"requirements": { "id": "/^[0-9]+$/" }`), as it does on a `DELETE` route without requirements and on every `GET` route. The router matched such a route in its own branch, which wrote the values to `req.delete` only, so `req.params.id` was undefined there. A placeholder the route does not bind in `param` stays out of `req.params`, as on `GET`. Browser-bundled: restart the bundle and rebuild your bundles (`gina bundle:build`) to pick it up. (#B955)
* A DELETE route whose `requirements` cover only some of its URL placeholders now matches. The router matches a DELETE route that declares `requirements` in a branch of its own, which skipped a placeholder without a requirement instead of scoring it, so such a route answered 404 on every request while the same route on GET matched; the branch now accepts any non-empty segment for that placeholder, as the GET path does, and sets `req.delete` and `req.params` from it. The browser bundle carries the router: restart and re-bake your bundles (#B956).
* A template that a route middleware renders with `self.render()` now sees the filters, tags and extensions the bundle registers in `controllers/setup.js`, from the first request after a boot. The router runs `setup.js` only for a request that reaches a controller action, after the route middlewares, so such a template answered a 500 `Invalid filter` until a request had reached an action in the same process, and on every request for a route set whose middleware renders them all. A swig render now runs `setup.js` on its engine when that engine has not run it yet, with the members the router hands it; an action request still runs it once, and a filter named like one of gina's own still loses to gina's. Restart your bundles (#TPL3).
* In an edit form, the delete link of a saved file now goes away when a new selection replaces that file, wherever the link sits. The staging success empties the preview container, which took a delete link placed inside it but not one placed after it (the shape the uploads guide documents), so that link stayed on the page, bound to a file the input no longer held: activating it sent no request, removed nothing, and logged the zero-match warning. The replaced entries are kept on the input until a staging succeeds, over a failed staging or an empty selection, and their links are then removed as a delete removes one. Re-bake your bundles (#B150).
* A staged file input's reset and delete links keep working after a `change` that carries no file (an emptied selection). Such a change emptied the input's record of the files it shows while their previews and hidden fields stayed in the form, so a reset or delete link then sent no request, removed nothing, and logged the zero-match warning. The listener now returns before it writes anything. Re-bake your bundles (#B959).
* A staged file input now changes the page and the form only when a new selection's staging succeeds: a failed staging changes nothing, and the files shown keep working while a file uploads. A failed staging emptied the preview container, taking the previews of the files still in the form, and any reset or delete link inside it, off the page; a saved file's delete link placed after the container then sent no request; and the hidden fields the failed selection had added were submitted empty. While a staging was on the wire, a saved file's delete link sent no request, and a staged file's reset also took the new file's hidden fields out of the form, so the form submitted no file while the page showed one. A new selection's hidden fields are now written when its staging succeeds. Re-bake your bundles (#B960, #B961).
* A staged file input's `name` field now takes the staging answer's `name`, like every other field, so a new file chosen in an edit form submits its own name rather than the saved file's. The field was filled only while it was empty: an edit form that declares it submitted the saved file's name beside the new file's location and original filename, and a second file chosen on the same input submitted the first file's name. A staging answer without a `name` key leaves the field as it is, so a page that relied on a declared `name` surviving a replacement can keep that value in a field the answer does not return. Re-bake your bundles (#B962).
* A `POST` or `PATCH` whose body is a top-level JSON array (`[{"a":"1"},2]`, whatever its content type, `application/json` included) now reaches the action as that array in `req.post` / `req.patch` on every request, the same object as `req.body`. The first request to each path got an object keyed by index (`{ "0": …, "1": … }`), a separate object from `req.body`, while every later request to the path got the array; on a route with URL placeholders each new value is a new path, and a `true`, `false` or `on` segment beside the array was a boolean on that first request only. The route's URL placeholders are now named properties of the array on every request, with the 0.7.6 `true` / `false` / `on` rule; one named like a property of the array itself (`length`, `map`, …) or with digits only (`:5`) is in `req.params` only, on every request. A `PUT` is unchanged: `req.put` and `req.body` hold an object keyed by index. Server-side: restart the bundle to pick it up. (#B953, #B965)
* A popin can be closed again after a link inside it loaded a page. A plain link in popin content (an `<a href>` with no `id`, no `#` and no `target`) loads its page into the same popin; after such a load, landed or failed, Escape closed the `<dialog>` while the popin stayed open (no `close` event, and its trigger could no longer show it), Escape on a non-modal popin did nothing, and `gina.popin.close(name)`, a form's `close()` and a client navigation (which closes the open popin through that call) did nothing at all. The same held after `gina.popin.load()` reloaded an open popin, after a link load into a `data-gina-dialog-target` popin, after a link with a `target`, and after a form's redirect into its own popin. A close while such a load was in flight let the late answer fill the closed popin, or reopen a declarative one. Since 0.7.6 every close works once the load has settled, Escape and the close button also close while it is in flight, and a close drops the late answer; `gina.popin.close(name)` and a form's `close()` are still ignored while the load is in flight. Browser-bundled: restart the bundle and re-bake it (`gina bundle:build`) to pick it up. (#B974, #B975)
* Gina now requires `@rhinostone/swig` `^2.9.6` in both manifests, which carries the fixes of 2.9.4. On the default render path, swig up to 2.9.3 dropped what a template had rendered before an `{% import %}`: the output above the tag, the layout's output before a block that holds one, every item of a `for` loop that holds one, and a macro's output before the tag; an import at the very top of a template was not affected. 2.9.4 keeps that output, so a template whose import follows other output now renders it (a comment and blank lines above the import come out as those blank lines). On the async loader path (`settings.template.swig.loader`), swig up to 2.9.3 failed to compile a template with an `{% include %}` or `{% import %}` inside a `for` loop or a `filter` tag, or an `{% include %}`, `{% import %}` or `{% block %}` anywhere in a macro body, even when the macro was never called; 2.9.4 renders the loop and filter cases and a template that only defines such a macro, and calling the macro throws an error that names it and its template. Upgrading gina installs 2.9.6 or later (a project copy loaded through `swig.useProject`, or a frontend selected through `swig.package`, keeps its own version, so update it there); restart the bundle. (#B978, #B997)
* A `self.query()` call over HTTP/2 that is retried after a 502, a stream error or a stream that ended early now leaves its session to the other calls in flight on it: the session is dropped from the cache and closed once they have answered. Before, the retry destroyed the session and those calls failed with a 500 (a typed `STREAM_ERROR` on Bun 1.4, a 500 with no error code elsewhere); a session error or a connection reset still closes the session at once. A call that was never sent, still waiting for a session that never connected when gina dropped that session (at another call's timeout or, on Bun, at the keepalive deadline), is now sent again on a new session whatever its method (on Bun it failed with a 500). A stream that ends without its response (a reset before any response, or its session destroyed under it) now follows the premature-close rule: a safe method, or a call with `retryUnsafe: true`, is sent up to twice more, then the call fails with `PREMATURE_CLOSE` (503); before, it came back as `{ status: 200, empty: true }` or as a 500, so an upstream that resets a stream before answering (with `NO_ERROR`, or on Bun with any code) now receives a safe method up to three times. On Bun 1.2 and 1.3, an empty response now comes back as `{ status: 200, empty: true }` as on Node.js, where it was a 500, and a refused connection or a failed TLS handshake gets its typed error (`ECONNREFUSED` 503, `STREAM_ERROR` 500), where it was a 500 with no error code or, for a failed handshake on 1.2.21, an empty success; neither is sent again. Known limit on Bun 1.2 and 1.3: an empty response that completes while its session is being closed after another call's retry is read as incomplete (a safe method is sent again, an unsafe one fails with `PREMATURE_CLOSE`). Server-side only: a running bundle picks this up at its next restart. (#B981, #B968, #B628, #B982)
* The form validator's upload trigger warning now names only a control the page has to provide: a saved file's delete link, or an id declared with `data-gina-form-upload-reset-trigger` or `data-gina-form-upload-delete-trigger` that matches no element. It warned "did not find `upload reset trigger`" at the first selection of every upload input, for the reset control Gina adds itself once the staging succeeds (twice when the input had no preview container), and a `$forms[id].reBind()` of an edit form warned "did not find `upload delete trigger`" for a saved file's delete link that was on the page and already bound. Removing a file works as before. One case still warns: a `reBind()` after a file was staged reads the staged file's preview as a saved file and looks for its delete link. Re-bake your bundles (#B292).
* A click on an element inside a popin link that has a `target` (an icon, or a `<span>` label in `<a href="…" target="_blank">`) now opens that window, as a click on the link itself does. The popin read the link's `href` and `target` from the element clicked, which carries neither, so such a click loaded the link's page into the popin instead. A plain link (no `id`, no `#` and no `target`) still loads its page into the same popin, whichever element inside it is clicked. Browser-bundled: restart the bundle and re-bake it (`gina bundle:build`) to pick it up. (#B977)
* `self.throwError()` no longer writes into the error object an action passes it. Up to 0.7.5 the one-argument form `self.throwError({ error, fields })`, and its `flash` and `errors` variants, combined that object with gina's own error data by writing into it: the object received the response's `status` and incident `ref`, on an HTML request a `stack`, and on a custom error page that page's data (`isRenderingCustomError`, `bundle`, `pathname`, `title`). An object an action passes on more than one request, such as a module-level error object, then answered later requests with the first request's incident ref, on the JSON body and on the error page, and on an HTML request it lost its `fields`, because the `stack` the first request left in it sent the later ones down another branch; a frozen object made `throwError()` itself throw. In the local scope the built-in error page also wrote its trimmed stack text back into the `stack` of an `Error` or a plain object passed in the three-argument form `self.throwError(res, code, err)`, at every call. gina now combines a copy of the object, one level deep (its members are shared), and trims a local copy of the stack. A `ref` the object carries is still honoured; an action that read the incident ref back from its own object after `throwError()` sets its own `ref` on the object instead. A class instance passed as the object is not copied and keeps the old behaviour. Restart your bundles (#B672).
* With an async swig loader (`settings.template.swig.loader`) and with nunjucks (`render.engine: nunjucks`, with or without `settings.template.nunjucks.loader`), a page rendered for a request that has a session now gets the request's session block under `page.data.session` (`id`, `lastModified`, `createdAt`, `expiresAt`, `timeout`), as with the default swig renderer. Up to 0.7.5 those three renderers never built it: a template read no session value, and the client bootstrap in the page kept its `{{ page.data.session.id }}`, `.timeout`, `.createdAt` and `.lastModified` placeholders as written, so in the browser `gina.session.id` was that text and `gina.session.timeout` was `NaN`. An action's own `session` member keeps its keys and gets the keys of the block it lacks, an action's own `page.data` member gets the block, and the object the action passes is not written. A page without a session, or with a session whose store sets no `createdAt` or `lastModified`, now gets empty values in the bootstrap instead of the placeholders. Restart your bundles (#B989).
### Security
* Gina now requires `@rhinostone/swig` `^2.9.6` in both manifests. Up to 2.9.0, swig's `striptags` filter ran in time quadratic in the length of its input: on text with many `<` and no `>` after them, 100,000 characters took about four seconds, so a template that applied `striptags` to request data could be made to block the event loop. 2.9.1 runs it in linear time with the same output (advisory GHSA-rvx7-jqr9-c242). Gina's own code and templates never call `striptags`. Up to 2.9.1, `@rhinostone/swig-core` built a range of any size, so a large bound from template data could exhaust the heap (advisory GHSA-f8f4-95q3-38qw): native swig has no range syntax, so gina's rendering never reaches that code, and 2.9.2 returns an empty range above 1,000,000 elements. Up to 2.9.4, nothing bounded how deeply templates nested on swig's async render path, so a template that includes, imports or extends itself, directly or through another template, loaded templates until the heap ran out and the process aborted (advisory GHSA-86pr-x856-xrq5): gina renders on that path when a bundle sets `settings.template.swig.loader`, and 2.9.5 fails such a render once more than 1,000 templates are nested, or at once for an `extends` cycle. Up to 2.9.4, with swig's memory compile cache, the first page that overrode a block nested inside a tag of a cached layout put its override into that layout, so other pages extending it showed that page's block (advisory GHSA-g628-5x3r-g298): gina builds the engines of both its render paths with `cache: false`, so its rendering never reaches that code. Up to 2.9.5, swig rendered on the locals object a caller passed, so a name a template set (`{% set %}`, a macro, an import, a loop variable) landed in that object and a later render given the same object read it, and with swig's memory compile cache a compile given locals in its options kept them for later compiles of the same file (advisory GHSA-25w8-77gg-4ccw): gina's own copy keeps a plain object an action passes to `self.render()` unwritten (#B988) and returns a class instance as is, which 2.9.6 covers by rendering on a copy of the locals made at the top of each render, and gina compiles with `cache: false`, so its rendering never reaches the cached case. 2.9.6 also changes what a template sees: a top-level property of the locals that is not enumerable is no longer visible, a top-level getter is read once per render, and on the async render path `{% parent %}` renders the block above, a macro that holds `{% parent %}` throws, and an imported template's own sets stay out of the template that imports it. Upgrading gina installs 2.9.6 or later (a project copy loaded through `swig.useProject`, or a frontend selected through `swig.package`, keeps its own version, so update it there to 2.9.6, which also carries the frontend fixes of 2.9.3: filters in all three, Twig ranges and `batch`, Jinja2 `slice` and `batch`, and Jinja2 and Django `for` loops); restart the bundle. (#B963, #B973, #B978, #B983, #B997)
* `self.render()` and `self.renderWithoutLayout()` no longer write into the object an action passes them. Up to 0.7.5 the render combined that object with gina's own page data by writing into it: the default swig renderer added the request's session block (`page.data.session`, with the session id), its `page.view` and, with the Csrf plugin adopted, its `gina.csrfToken` and `gina.csrfInput`; the nunjucks renderers and the async swig renderer wrote the request's Csrf values into an object's own `gina` member, and its `page.view` values into an object's own `page.view` member. Because the combine keeps a value that is already there, an object an action passes to more than one render (a module-level object, a `require()`d JSON module) carried the first request's session id, CSRF token and URL into the pages of later requests, the client bootstrap's `gina.session` included. The session cookie stays signed, so the id alone does not open the session. Each render now combines a copy: the object itself, its `page`, `page.view`, `page.data`, `page.environment`, `gina` and `session` members, and every member gina's data also holds are new for the render, and everything else is shared, so a template reads the same values as before. What changes: a change the action makes to the object after calling the render, at its top level or in those members, may no longer reach the template, the object no longer gains `page`, `gina` or `session` keys, and an object frozen with `Object.freeze()` renders where a render that had to add a key to it failed with a 500. A class instance passed as the object, or placed at one of those paths, is not copied and keeps the old behaviour. Restart your bundles. A security advisory accompanies this fix: [GHSA-2jvf-v3wm-pc9p](https://github.com/gina-io/gina/security/advisories/GHSA-2jvf-v3wm-pc9p) (#B988).
* `self.renderJSON()` no longer writes its Inspector sidecars into the object an action passes it. In development, and during a production instrumentation window for a request carrying `x-gina-inspector: true`, renderJSON adds the request's query log (`__ginaQueries`: each statement's text and its parameter shapes, or its values with `inspector.queries.captureValues`) and its timeline (`__ginaFlow`) to the response object when they are not empty. Up to 0.7.5 it added them to the action's own object, so an object an action passes to more than one renderJSON call, such as a memoized or cached response object, kept the first request's sidecars and sent them in every later response built from it, to any client, external ones included, and after the window had closed. renderJSON now writes the sidecars into a copy of the object, made once per response, one level deep (its members are shared). A class instance passed as the object is not copied and keeps the old behaviour. Restart your bundles. A security advisory accompanies this fix: [GHSA-2jvf-v3wm-pc9p](https://github.com/gina-io/gina/security/advisories/GHSA-2jvf-v3wm-pc9p) (#B992).
