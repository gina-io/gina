## 0.7.7 - 2026-10-29
### Changed
* Gina now requires `@rhinostone/swig` `^2.9.11` in both manifests (#B1022). Swig 2.9.11 is a fix release, with no advisory, that changes what some native swig templates render. A filter in a `set`, `if`, `elseif`, `for`, `include` or `filter` tag argument now applies to its own operand, as in an output: `{% set y = arr[0]|upper %}` over an empty array no longer throws, shapes such as `{% for c in (x)|reverse %}` or `{% include name|default("p.html") %}` now compile, and a filter after a function or method call with an expression before it now applies to that call only, in a `set`, `if`, `elseif` or `for` argument alike, where it applied to the whole expression before it: `{% set y = a + f(x)|upper %}` with `a = "x"` and `x = "ab"` gives `xAB`, where it gave `XAB`, and `{% if z and f(x)|upper %}` with `z = 0` is now false. A filter after a literal in an output that holds an operator or a ternary applies to the literal: `{{ 3|default(1) + 1 }}` gives 4, where it gave 3. An output whose variable is followed by a filter renders an empty string when the last filter returns undefined or null, for example `{{ items|first }}` over an empty array, or a custom filter that returns nothing; swig printed the word undefined or null. Inside an `{% autoescape true %}` region, a missing subscript or member, or a call that returns undefined, renders an empty string; gina's own `settings.swig.autoescape` is a boolean, which already did. Gina's own templates use none of these shapes. Upgrading gina installs 2.9.11 or later (a project copy loaded through `swig.useProject`, or a frontend selected through `swig.package`, keeps its own version); restart your bundles.
### Fixed
* Over HTTP/2, a success answer now declares its `content-length`, as it already did over HTTP/1.1 (#B1005): `renderJSON()`, `render()` with swig or nunjucks (with or without an async loader), `renderXML()`, and an answer served from the render cache. A client can then tell a body cut short from a complete one, which gina's own `self.query()` does since this release. A 204, 205 or 304 answer still declares none: a Node.js HTTP/2 client resets a 204 or 205 that declares a length. `renderStream()` still sends no length.
* An HTTP/2 `self.query()` response whose body is cut short mid-transfer is no longer delivered as a success (#B985). A body shorter than the response's `content-length`, and any body on a session gina tore down itself (its keepalive or pre-flight PING deadline, a stream error that ends the session, the boot warmup's deadline), now follow the premature-close rule: a safe method, or a call with `retryUnsafe`, is sent again on a fresh session, and any other call fails `PREMATURE_CLOSE` (503). Up to 0.7.6 the caller got the partial body as a success, or an uncoded `{ status: 500 }` when it was JSON. On Bun 1.2 and 1.3, an empty response that completes while its session is being closed is no longer read as incomplete. A body sent with no `content-length` and cut by the connection closing or resetting is still delivered as received.
* A click on markup added inside a popin close button that is also a legacy trigger (a `.gina-popin-close` element carrying `data-gina-popin-name`), after that trigger was registered, now dispatches the trigger, as a click on the button itself does. The popin read the trigger's event name from the element clicked, so a node added later (an icon, a label) matched nothing and the click did nothing; markup already inside the button when the trigger was registered was not affected. Browser-bundled: restart the bundle and re-bake it (`gina bundle:build`) to pick it up. (#B995)
* An element carrying `disabled` (any value but "false") in popin content now does nothing when clicked, wherever the click lands on it, for a link with an `href` and for a `gina-popin-close` element. Before, a link carrying `disabled` when the popin content was loaded was left to the browser, so a click on it followed the link in the whole page or opened its `target` window, and it stayed that way once `disabled` was removed; on a link that became disabled later, a click on an icon or a `<span>` inside it loaded the link into the popin, and a click on the link itself, although ignored, left the popin unable to close through `gina.popin.close(name)` or a form's `close()`; and a click on markup inside a disabled close element closed the popin. A link whose `disabled` is removed, or that carries `disabled="false"`, now works as the same link without it: it loads into the popin or opens its `target` window, and a link carrying its own `id` closes the popin, as it already did when it was never disabled. An `<a>` with no `href` that carries `disabled` is still left as written. Browser-bundled: restart the bundle and re-bake it (`gina bundle:build`) to pick it up. (#B994, #B1007, #B1008)
* A click on an `<a>` with no `href`, or with `href=""`, in popin content no longer leaves the popin unable to close. Before, `gina.popin.close(name)` and a form's `close()` did nothing after such a click, a close from the anchor's own click handler included, because the popin waited for a load that never came. Such an anchor still loads nothing and keeps the `href="#"` Gina gives it, until the page gives it a real `href` (#B1015); in a popin registered with the validator, its click no longer appends the inherited data of the form around it to that `href` (a link's load still carries it). Browser-bundled: restart the bundle and re-bake it (`gina bundle:build`) to pick it up. (#B1012)
* An `<a>` in popin content that has no `href` when the content is bound, and is given one by the page afterwards, now works when clicked. Before, its click did nothing, and `gina.popin.close(name)` and a form's `close()` were ignored afterwards. It now follows the rules of a link: its page loads into the popin, and one carrying a `target`, a `download`, a `#` in its URL or a URL scheme other than http(s) is left to the browser, which opens that window, saves the file, moves to the fragment or hands the URL to its handler. This also holds after a partial swap of the popin (`data-gina-dialog-target`). Its load carries no `?inheritedData`, even inside a form carrying inherited data in a popin registered with the validator. An anchor carrying `disabled` still does nothing. Browser-bundled: restart the bundle and re-bake it (`gina bundle:build`) to pick it up. (#B1015)
* A link carrying `download` in popin content is now left to the browser, which saves the file. Before, its click loaded the file into the popin by XHR and wrote its bytes there. Inside a form carrying inherited data, in a popin registered with the validator, such a link is saved from its `href` as written, with no `?inheritedData`. A link that carries its own `id` is handled as before: its click closes the popin. Browser-bundled: restart the bundle and re-bake it (`gina bundle:build`) to pick it up. (#B1016)
* A link in popin content whose URL has a scheme other than http(s) (`mailto:`, `tel:`, `javascript:`) is now left to the browser, as it is outside a popin. Before, its click fetched the URL by XHR, which failed with an error and opened nothing. The test reads the `href` as written, so a URL written with leading spaces is still fetched. Browser-bundled: restart the bundle and re-bake it (`gina bundle:build`) to pick it up. (#B1018)
* A `self.query()` answer with a 4xx or 5xx status whose body carries no gina `status` (an empty body, text, JSON without `status`, the HTML page a proxy in front of a bundle answers with itself) now reaches the caller as an error carrying that status, on HTTP/1.1 and HTTP/2 (#B984): `{ status, error, message }`, with `error` the label `core/status.codes` gives the status and `message` the body text, the JSON text, or the label for an empty body. The promisified call rejects with it, an `.onComplete()` handle receives it as `err`, and a `forward` route answers it through `throwError()` with its status, where it relayed it to the client as a 200 carrying the body. Up to 0.7.6 only the body's `status` was read, so such an answer was delivered as a success: an empty one as `{ status: 200, empty: true }` over HTTP/2 and as an empty string over HTTP/1.1, any other with its body. A body carrying `status` still decides, and a status the map does not know (such as 599) is still delivered as a success.
### Security
* `self.renderJSON()` no longer adds its Inspector sidecars to a response during a production instrumentation window. Up to 0.7.6, while a window opened through `/_gina/instrument` was open, renderJSON added the request's query log (`__ginaQueries`: each statement's text, its parameter shapes or, with `inspector.queries.captureValues`, its values, the `.sql` file's server path, the bundle and connector names and the result counts) and its timeline (`__ginaFlow`) to the JSON response of any request carrying `x-gina-inspector: true`. `self.query()` sends that header on a call to another bundle so that the caller can merge the callee's capture into its own, but any client can send it, so during a window an unauthenticated client could read its own request's query log and timeline. The sidecars are now added in development only. During a window the capture leaves only over the authenticated `/_gina/agent` channel, and a caller's Inspector no longer shows the queries and timeline of a bundle it calls: open a window on each bundle that serves the page. Affects 0.4.0 to 0.7.6, for a bundle that enables `inspector.instrumentation` and while a window is open; development is unchanged. Restart your bundles. A security advisory accompanies this fix: [GHSA-jhw4-95q6-2rhv](https://github.com/gina-io/gina/security/advisories/GHSA-jhw4-95q6-2rhv) (#B993).
* Gina now requires `ws` `^8.22.0` in both manifests (#B1024), so installing gina 0.7.7 moves a project off ws 8.21.0 even when its lockfile pins it. ws 8.21.1 lowered the default `maxBufferedChunks` and `maxFragments` limits and counts empty fragments toward them, completing the fix of GHSA-96hv-2xvq-fx4p: under the 8.21.0 defaults, a client sending many fragments could still exhaust a WebSocket server's memory (ws issue #2331). Gina's WebSocket servers run on those defaults: the Inspector's agent channel (refused outside development unless it is enabled with its key) and the engine.io server an application starts through `ioServer`. No advisory names 8.21.0. Restart your bundles.
