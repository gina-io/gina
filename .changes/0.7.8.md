## 0.7.8 - 2026-11-02
### Changed
* Gina now requires `@rhinostone/swig` `^2.11.0` in both manifests (#B1034, #B1072). Native swig templates change between 2.9.11 and 2.11.0 through 2.9.12 and 2.9.13, fix releases with no advisory; 2.10.0 and 2.11.0 themselves change only the frontends: 2.10.0 swig-twig, swig-jinja2 and swig-django; 2.11.0 swig-jinja2 and swig-django, whose `==`, `!=` and `in` now compare with Python's equality, and swig-jinja2 gains Jinja2's comparison tests (`x is eq 1`). What a native template can render differently: `date` of a missing, null, empty or unparseable value renders an empty string, where it printed `NaN/NaN/NaN`. A filter or call result that is undefined or null reads as an empty string at a `+` or unary operand, in outputs and in `set` arguments alike: `{{ "a" + f() }}` renders `a`, where it printed `aundefined`, `{{ 1 + f() }}` renders 1 and `{{ -f() }}` renders 0, where they printed NaN. A filter after a filter or a call that found nothing renders an empty string: `{{ items|first|lower }}` over an empty array threw, and `{{ f()|upper }}` with a null result printed `[object Object]`. `first`, `last` and `replace` give an empty string for an undefined or null input, and `length` gives 0, where they threw. Blocks nested in blocks follow one chain of definitions per block name: a block nested in any block of an extending template defines its name even when the root has no block for the enclosing one, `{% parent %}` in a block nested in an override renders the next definition of its name, where it rendered nothing, as does `{% parent %}` in an override of a nested block on the sync path, as the async path already did, and a block that renders itself through a nested block or `{% parent %}` fails with an error naming the block, where the render overflowed the stack. The engines gina builds pass `cache: false`, so the template cache that swig 2.9.13 added to its async loader path does not engage: a layout and an include are still loaded on every render. Gina's own templates use none of these shapes. Upgrading gina installs 2.11.0 or later (a project copy loaded through `swig.useProject`, or a frontend selected through `swig.package`, keeps its own version); restart your bundles.
### Fixed
* An HTTP/1.1 `self.query()` call that reaches its `requestTimeout` now fails with an error that names the timeout (#B969): a native `Error` whose `code` is `ETIMEDOUT`, with `status` 503, `retryCount` (the attempt it was on) and the message « [HTTP1] No response from <hostname> after <time> ». Up to 0.7.7 the timeout failed like a reset connection, `ECONNRESET` « socket hang up », which reads « `Controller::query()` could not connect to [ … ] using port N » when the port belongs to a bundle; it carried no `status`, so `throwError(err)` and an `.onComplete()` handle answered 500 where they now answer 503, the status of an HTTP/2 timeout. A response whose headers had arrived before the timeout and whose body then stalled never called back at all; it now fails with the same error. The re-send rule is unchanged: a GET, HEAD, OPTIONS or TRACE, or a call with `retryUnsafe`, is still re-sent (twice by default) before the error is delivered, a refused connection still reads « could not connect », and the `server.query.circuitBreaker` circuit breaker still counts the timeout.
* A form re-bound while one of its file inputs shows files the user staged keeps those files (#B990). `$forms[id].reBind()`, `.bind()`, or `destroy()` followed by `validateFormById()`, read the staged previews in `<input id>-preview` as saved files: a file shown without an image (a PDF whose staging answer carries no `preview` thumbnail) lost its entry, so its reset control removed nothing and the form still saved the file the user had removed; beside an image on a `multiple` input, its reset removed the image instead and the form still saved the PDF; and an image staged logged « did not find `upload delete trigger` » for a delete link the page never had. A re-bind now leaves the input's staged files as they are while their reset controls are on the page. Once the page has replaced the preview container, for instance to show the saved file after a save, the container is read again as before, and a form re-bound before any staging or after a reset is unchanged.
* `Collection.notIn()` and `delete()` on an empty source now return `[]` (#B1029). Up to 0.7.7 the array form, `notIn(rows, key)` (also with no key, or with `false`), returned `rows` itself when the searched array was empty, a new Collection over `[]` or an empty query result chained into `notIn`, so the call handed back the very rows it excludes, none of which belong to the source; `delete(rows, key)` delegates to `notIn` and did the same. The filter-object form, `notIn({ … })`, already returned `[]`. This changes the result for code that relied on the old one: a caller that wants the excluded rows when the source is empty now takes them directly. `lib/collection` ships in the browser bundle, so the pickup is a bundle restart and a re-bake.
* A reset no longer names a staged file or its preview « undefined » when the staging answer gives no name for it (#B1027). The staging success wrote the answer's `originalFilename` and its preview's `originalFilename` into the preview node without a check, so a missing name was stored as the text « undefined », and the reset sent it in its removal request and in the removal callback's `payload.files`. The guide's `preview` example carries no `originalFilename`, so a reset of a file staged with that shape named its preview « undefined ». A name is now recorded only when the answer gives one: a preview without one is left out of the removal request, and a file the answer left unnamed is named by the browser file's name.
* An error that reaches the server's error responder as an `Error` object now answers with its text (#B841): the JSON error body read `"error":{}` and a custom error page printed `[object Object]` as its message. It reached this way: a POST or PATCH whose `application/json` body does not parse, a `requireController()` call whose controller throws while it is built, and a bundle's `controllers/setup.js` calling `this.throwError(res, code, err)` with an `Error`. The text is the error's stack in the local scope and its first line elsewhere, as for an error passed as `err.stack`. Outside the local scope the error object passed in also keeps its `stack`, which the responder deleted.
* With the swig engine, an action that renders request data, such as `self.render(req.get)`, no longer switches into error-page rendering when the request carries `isRenderingCustomError=true` (#B873): such a request answered 500. Only gina's own error-page rendering sets that mode now, as with the nunjucks engine.
* The `length` template filter now returns a string's length, on swig and on nunjucks (#B846). Up to 0.7.7, `{{ "abc" | length }}` rendered empty, `{% if title | length %}` was false for any string, and the documented `{{ "hello" | length }}` rendered empty instead of 5; only a string that reads as JSON, such as `'{"a":1}'` or `"5"`, gave its length. On nunjucks a string passed through `| safe` now counts its characters as well (a JSON-looking one counted 2). Swig hands a filter an empty string for a missing or null variable, so on swig `{{ missing | length }}` now renders 0 where it rendered empty, and `{{ missing | length | default("No") }}` gives 0 instead of "No", as swig's own `length` filter does; `{% if missing | length %}` stays false. Arrays, objects and collections count as before.
* A fill-only `merge()` (the default mode) now keeps a source key named after an `Object.prototype` member — `toString`, `valueOf`, `isPrototypeOf`, `hasOwnProperty`, `propertyIsEnumerable`, or gina's own `count` — when the target holds that name only through `Object.prototype`: the merge read the inherited function as an existing value and wrote it back as an own key, so the source's value was lost and JSON output omitted the key; a PUT form or JSON field so named reached the action as nothing. A target that owns the key, or inherits it from its own prototype (an entity's query methods, a class's own `toString`), keeps winning as documented. `lib/merge` is in the browser bundle: pickup is a bundle restart and a re-bake (#B845).
* Two more places lost a key named after an `Object.prototype` member. `merge()`'s array-element fill tested ownership with the element's own `hasOwnProperty`, so a PUT body such as `list[0][hasOwnProperty]=1&list[0][b]=2` answered 500 « newTarget[a].hasOwnProperty is not a function »; it now tests through the built-in and keeps both keys. And `JSON.clone` — the server's and the browser bundle's — filled a key only when the target had no value for it, read through the prototype chain, so a cloned object lost `toString`, `valueOf`, `hasOwnProperty` or `count` to the inherited function; it now fills a key the target does not own. A GET `inheritedData` carrying `toString` (top-level or nested) or a nested `hasOwnProperty` reaches the action whole. Pickup is a bundle restart and a re-bake (#B849).
* A form reset no longer runs the live check (#B1037). `form.reset()`, a click on a reset button and the handle's `.resetFields()` restore the values, clear the error display and the `errors` store, and re-read the submit trigger, with nothing painted or announced. Up to 0.7.7 each field ran its own live pass: the live region announced an error and kept it, a required value-carrying checkbox or radio stayed painted, and `.resetFields()` alone left every empty required field painted. A `query` verdict that comes back after a reset is dropped, and a submit it refuses paints nothing. The submit trigger is re-read also when the `query` field is not the last of its rule set (up to 0.7.7 it kept its state, and the first click on a valid form was refused) and once a master checkbox has applied its group; a request in flight keeps its trigger locked. With live check off, `.resetFields()` runs no check. A bound field removed from the page and an empty `<select>` no longer make the reset throw, which left nothing reset. `.resetFields()` still ends on each control's value at bind, and `form.reset()` still ends `text` and `hidden` inputs on their `defaultValue`.
* Two forms that share a field id no longer interfere on a reset, and the bind now says so (#B1036). Live checking keys its listeners on the id, so of two controls with one id only the first is live-checked; that stays, duplicate ids being invalid HTML. Up to 0.7.7 nothing said so, and the second form's `.resetFields()`, or a reset of that form, emptied the first form's field and painted its error. The bind now warns once per form and id, and a reset works on the form's own controls, also when an element that is not a control holds the id first in the page.
* A value written by a script no longer paints an error on a field nobody touched (#B1035). `el.value = …` still re-checks the form: the submit control opens or closes, the error is stored, and a click on a gated submit control reveals it. It paints nothing new: no message, no `aria-invalid`, nothing in the live region. A message already showing changes or clears. To show the error at once, dispatch a real `change` after the write. Up to 0.7.7 the write ran the live check as a user's change would, so the field showed its error and the live region announced it. A write to a `<textarea>`, or to a `tel`, `url`, `search`, `time`, `datetime-local`, `month` or `week` input, re-checks nothing, as before.
* A form no longer freezes the browser tab or sends `query` requests without end when a field's only rule is `query`, or when a `query` field also drives a `_case_` block (#B1039). On an otherwise valid form, the re-validation that follows a clean verdict asked the same `query` again, and its clean verdict started that re-validation again. With a value, the tab froze when the user typed, or at page load for a field last or alone in its rule set (0.6.7 to 0.7.7). With an empty field, requests streamed from page load (0.6.5 to 0.7.7). The re-validation no longer asks again a `query` whose answer is in. Workaround on a published version: add a sync rule such as `isRequired` or `isString` to the field; it does not help a field that drives a `_case_` block. The browser bundle changed: restart the bundles and re-bake.
* The browser no longer reports a failed routing fetch on a page that is going away, and a page whose fetch was cut gets its routing table (#B1044). A navigation can cut the fetch of `_gina/assets/routing.json` while a page boots. The page being left then printed « routing dependency failed to load » in the console. On WebKit, when that navigation did not replace the page (it answered a 204, or was a download), the page also stayed with no table, so client `getRoute()` and `toUrl()` stayed degraded until reload. A fetch that got no answer is now asked again after 300 ms, 1 s and 2.5 s before it counts as a failure. On a real network failure the error and the `gina.ready` handlers therefore come about 3.8 s later; an HTTP error or a body that is not JSON still fails at once. The browser bundle changed: restart the bundles and re-bake.
* `PathObject.mv()` and `.cp()` no longer destroy a path when the target already is the source (#B1046). `mv(x, x)` copied the file onto itself and then removed it, and `mv(dir, dir)` and `cp(dir, dir)` removed the folder before copying from it; all of them reported a success. Such a call is now a no-op that reports a success. A file moved to the folder it already sits in, which landed on itself and was then removed, stays too. A rename that only changes the case, which destroyed the path on a case-insensitive filesystem, now renames. The same file by another spelling or through a symlinked parent counts as the same path, and so does a hard link of it, which is now left in place with the source. Server-side: a bundle restart picks it up.
* A folder `cp()` or `mv()` now reports a file it could not copy, and `mv()` keeps its source (#B1047). The walk dropped the error, so moving a folder that held an unreadable file reported a success and then removed the source, and the file was gone. The walk still copies everything it can and reports its first failure at the end. A failed `readdir` or `lstat` during the walk, or a symlink that resolves to nothing, threw from an async callback, and an existing destination that could not be cleared called `process.exit(1)`; each now reaches the callback. Check your builds: `bundle:build`, `project:build`, `bundle:copy` and `bundle:add` now fail on a file they could not read, where they silently left it out. Server-side: a bundle restart picks it up.
* `PathObject.mkdir()` now calls back on a failure (#B1048). The callback never ran when the folder could not be created, for instance under a read-only parent, or for one of two concurrent calls of the same path. A failure now reaches the callback, and two concurrent calls both succeed. A folder `cp()` or `mv()` whose destination cannot be created now reports it and copies nothing. Server-side: a bundle restart picks it up.
* `PathObject.cp()` and `.mv()` now refuse a folder copied or moved onto a folder that holds it, or into itself (#B1050). The copy clears an existing destination first, so `cp(parent/child, parent)` destroyed the whole of `parent`, source included, and then threw from an async callback as an uncaught exception. A folder copied into itself walked its own copy until the path was too long, never called back, and left that nest on disk. Both now reach the callback with an `Error` coded `EINVAL` before anything is written, whatever the spelling, the case or a symlinked parent. A `.cp()` into itself with an `excluded` list still runs, since the list can leave the destination out of the walk. Server-side: a bundle restart picks it up.
* On Bun, an HTTP/2 `self.query()` call's `requestTimeout` now belongs to that call (#B971). Bun's `ClientHttp2Stream.setTimeout()` sets the session's one timer, so up to 0.7.7 a timeout could fire late or for the wrong call: a hung call beside a sibling that finished first never called back on Bun 1.4 and failed late on Bun 1.2 and 1.3; a call with a long timeout failed at a sibling's short one, with a message naming its own; on Bun 1.4 a timeout above 5 s, the default 10 s included, never fired, because the keepalive PING refreshed the timer; a response still streaming past the timeout failed mid-body; on Bun 1.2 and 1.3 a slow upload failed at the timeout; and each call left a `timeout` listener on the session or its socket. A stream now has its own timer on Bun, following what Node.js does: response headers do not refresh it, data and the completed upload do, and an upload that still moves does not time out. Node.js is unchanged. Server-side: restart the bundle.
* On Node.js 24, Node.js 26 and Bun 1.4, an HTTP/2 `self.query()` call sent on a session that had just been destroyed is now re-sent on a fresh session, as the HTTP/2 resilience guide describes (#B1054). Up to 0.7.7, on a connection that had silently dropped, a call whose pre-flight PING was pending when the keepalive deadline destroyed the session failed with a 500 `STREAM_ERROR` « The session has been destroyed », for any method, though nothing had been sent. Node.js 22 and 25 and Bun 1.2 and 1.3 already recovered. Server-side: restart the bundle.
* On Safari, a live-checked `<input>` with `autocomplete="off"` (or `"false"`) behaves natively while it has focus (#B1064): Enter submits the form, `maxlength` holds, ArrowUp, ArrowDown and Shift with an arrow work, `input` and `beforeinput` fire for each key, and a `query` rule waits for the typing pause instead of sending one request per key. A `readonly` you write stays yours: in the markup or from a script, at any time, gina neither lifts it on focus nor replaces it on blur, where it used to lift it on every focus. The field itself is still `readonly` until it has focus, because Safari's form fill skips a readonly control; gina now writes that as `readonly="gina"`, which `[readonly]` selectors and the `readOnly` property still see, and which a selector on the old value, `[readonly="readonly"]`, no longer matches. Browser-bundled: restart the bundle and re-bake it (`gina bundle:build`).
* On Safari, Tab works on a live-checked `<input>` with `autocomplete="off"` (or `"false"`) (#B1063). It did nothing on `email`, `password`, `tel`, `number`, `url` and `search`; from a `text` field it skipped a `password`, an `email`, a `<textarea>` or a checkbox; and it stayed inside the form. Tab is native now, so it follows Safari's own order, which skips buttons unless the user turned them on in Safari's settings: gina's own Tab used to stop on a button. Browser-bundled: restart the bundle and re-bake it (`gina bundle:build`).
* On Safari, a live-checked `<input type="email">` or `<input type="number">` with `autocomplete="off"` (or `"false"`) now keeps what you type, in the order you typed it (#B1055). While such a field had focus, gina cancelled each key and rebuilt the value by hand. These two types have no text selection to place a character at, so `123` became `321`, was posted that way with no warning, and each key threw an uncaught `InvalidStateError`. The rebuild is gone: every key on such a field is native. Browser-bundled: restart the bundle and re-bake it (`gina bundle:build`).
* On Safari, a live-checked `<input>` with `autocomplete="off"` (or `"false"`) can still be typed into after `.destroy()` or `.unbind()` (#B1068). gina's own `readonly` stayed on the field with no listener left to lift it, so it took no keys while the form stayed on the page. Unbinding now removes that `readonly`; one you wrote stays, and binding the form again puts gina's back. Browser-bundled: restart the bundle and re-bake it (`gina bundle:build`).
* On Safari, a live-checked `<input>` with `autocomplete="off"` (or `"false"`) that already has focus when gina binds it can be typed into at once (#B1067). It took `readonly` with no `focusin` to come and lift it, so an `autofocus` field, or a field the user was typing in during a `.reBind()`, took no keys until it was left and focused again. It now takes `readonly` when it loses focus. Browser-bundled: restart the bundle and re-bake it (`gina bundle:build`).
### Security
* `PathObject.mv()` and `.rm()` now settle every call, whatever happens to the path meanwhile (#B1045). A source taken by another move or remove between the check in `mv()` and the copy threw from an async callback, past any `try` or callback, as an uncaught exception, which `lib/proc.js` answers by stopping the bundle. A path gone before the remove reached it, or a failed `lstat` or `readdir` during the remove, never called back, so the move or remove never completed. A path another operation takes now counts as done: a move whose copy finished reports a success. Any other failure reaches the callback, including a denied `unlink`, which read as a success with the source still there. `mv()` with no callback now logs a failure where it threw. Server-side: a bundle restart picks it up. A security advisory accompanies this fix: [GHSA-f9cq-pr3p-c8vv](https://github.com/gina-io/gina/security/advisories/GHSA-f9cq-pr3p-c8vv).
* On Bun 1.4, an HTTP/2 `self.query()` session no longer stops sending at the upstream's stream limit (#B1052). Gina dropped every listener of a finished stream, and on Bun 1.4 one of them gives the stream's slot back to the count against the upstream's `SETTINGS_MAX_CONCURRENT_STREAMS`, so up to 0.7.7, after as many completed calls as that limit (256 against an Isaac upstream's default), every later call on the session waited for a slot that never came: it failed `TIMEOUT` with a short `requestTimeout`, never called back with the default one, and the session did not recover (6 minutes measured). A finished stream keeps its listeners on Bun. Node.js and Bun 1.2 and 1.3 were not affected. Server-side: restart the bundle. A security advisory accompanies this fix: [GHSA-vj89-h9p8-wcvc](https://github.com/gina-io/gina/security/advisories/GHSA-vj89-h9p8-wcvc).
* A multipart upload whose parse fails now stops at once (#B1062): the request stops feeding the parser, each write stream closes and every file the request staged is removed, the parts that had finished included. The client's answer is unchanged, HTTP 400. Pickup: a bundle restart, no re-bake. A security advisory accompanies this fix: [GHSA-6x9w-56x2-v24q](https://github.com/gina-io/gina/security/advisories/GHSA-6x9w-56x2-v24q).
* A multipart upload whose client goes away now stops the same way (#B1061), on HTTP/1.1 and HTTP/2: its write stream closes and the files it staged are removed. The normal end of an upload is unchanged. Pickup: a bundle restart, no re-bake. A security advisory accompanies this fix: [GHSA-6x9w-56x2-v24q](https://github.com/gina-io/gina/security/advisories/GHSA-6x9w-56x2-v24q).
* `upload.maxFieldsSize` now counts the bytes a multipart request sends (#B1056): past the cap the upload stops, the files it staged are removed, the request is answered HTTP 431 and cut: on HTTP/1.1 the connection closes, on HTTP/2 the request's stream stops being read while the session keeps serving its other streams, so a client still writing may read the close, or stall, instead of the answer. A request under the cap is unchanged. Pickup: a bundle restart, no re-bake. A security advisory accompanies this fix: [GHSA-6x9w-56x2-v24q](https://github.com/gina-io/gina/security/advisories/GHSA-6x9w-56x2-v24q).
* A download whose file name holds a character above U+00FF (a decomposed accent, a typographic apostrophe, CJK, emoji) now names the file (#B1073). `downloadFromURL`, `downloadFromLocal` and `serveFromStorage` wrote the name raw into the `Content-Disposition` header, which Node refuses on HTTP/1.1: the first two answered 500, and `serveFromStorage` with `download` or `filename` exited the bundle process, because it sets that header inside the storage driver's callback. On HTTP/2 the name came out mangled or missing. Such a name is now sent as a Latin-1 `filename` fallback followed by the RFC 8187 `filename*` parameter (UTF-8); a name Node already accepted keeps exactly the bytes it had, and a decomposed accent is normalised to its precomposed letter. A header error inside `serveFromStorage` now answers 500 instead of exiting the process. The browser bundle's XHR download path (`data-gina-link` links, form downloads) reads `filename*`. Pickup: a bundle restart and a re-bake. A security advisory accompanies this fix: [GHSA-p2qq-m2c6-54ch](https://github.com/gina-io/gina/security/advisories/GHSA-p2qq-m2c6-54ch).
