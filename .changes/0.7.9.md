## 0.7.9 - 2026-11-05
### Fixed
* A live check still on its way when its form is destroyed — a keystroke's check waiting out its one-second debounce, a radio or checkbox pick's, or the answer of a `query` rule — no longer throws an uncaught TypeError (« Cannot set properties of undefined (setting 'isValidating') », or « reading 'resetCount' »); neither does one whose field was moved out of its form in the meantime. The check now stops with the form; while the form stays bound, nothing changes (#B1069).
* An HTML request whose multipart upload stops while a file part is still being written now gets the bundle's custom error page for that stop: the 431 past `upload.maxFieldsSize` on a request that sends no `content-length`, or the 400 of a body that fails to parse after a large file part. The stop destroys that part's write stream, and its error could answer the built-in 500 page while the custom page was still being rendered; a JSON answer, sent at once, was not affected. Pickup: a bundle restart, no re-bake (#B1075).
* Changing a live-checked `<select>` no longer writes a page global named `once`. The select's whole-form check ended with an assignment to an undeclared `once`, so a page's own `window.once` was set to `false` after each select change, and a page that had no such variable got one. (#B1038)
* A form reset (`form.reset()`, a reset button, or the handle's `.resetFields()`) now restores a form-associated custom element through its own `formResetCallback`. The browser's native reset runs that callback; gina cancels the native reset and restores the bound controls itself, and it never ran it, so a component kept the value of its last commit and the reset's pass read that value: the submit control stayed open on an emptied required component. A component without a `formResetCallback` keeps its value, as a native reset leaves it, and a callback that throws is reported without stopping the reset of the other fields. As under a native reset, the callbacks run once every other control of the form is restored, and a component moved into another form after the form was bound is left to that form. (#B1041, #B1087)
* A form reset (`form.reset()`, a reset button, or the handle's `.resetFields()`) now drops a submit that waits for one of the form's staged uploads to finish, and releases the busy state that submit armed (`data-gina-loading` back to `false`), unless a request of the form's own is still in flight. The submit used to stay waiting: its trigger stayed busy after the reset, and when the upload succeeded the submit was replayed, posting the restored values with the staged file's metadata. (#B1043)
* A form's error callback (`data-gina-form-event-on-submit-error`, the `error.<id>` event) now says that the server answered and what it answered: whenever an answer came back, the payload carries `transportError: false` and `contentType` (the answer's `Content-Type` as the browser reads it, `null` when there is none; a JSON error body that carries its own `contentType` keeps it, except in an answer sent as an attachment). An answer that is not JSON, such as a reverse proxy's `502` page, still arrives whole in `message`, so check `contentType` before showing it. Before, a server error carried no `transportError` key at all, although the forms guide says `false` (a check `data.transportError === false` never matched), and nothing told a proxy's HTML page apart from a message the application wrote. An answer sent as an attachment now keeps a body that is not JSON in `message` too; that body used to be dropped. A failure to handle a `2xx` answer (a JSON body that does not parse), reported as `422`, carries both keys as well. (#B1083)
* A staged file input (`data-gina-form-upload-action`) whose staging failed now lets the same file be chosen again. The failed staging dropped the pending selection but left the input holding it, so its value still named the file, and choosing that file again staged nothing: Chromium fires `cancel`, not `change`, for a re-pick of the file an input already holds. The input's value is now emptied when its staging fails. The files it held before keep their previews, their reset or delete links and their fields, and a staging that a newer selection superseded leaves that selection on the input. A script that reads the input's `value` or `files` after a failed staging now finds them empty. (#B1059)
* A staged file input that held several files and then took a selection of fewer files no longer posts the files it replaced. The page showed the new files only, but the hidden fields of the indices the new selection no longer has stayed in the form, so the save posted the replaced files beside the new ones: three files staged, then one, posted all three. Those fields are now taken out when the new staging succeeds, as a reset takes them out: a field marked `data-gina-form-upload-is-locked` stays, and a later, larger selection brings back the fields the page declared at those indices. On an edit form that shows saved files, a selection of fewer files than the saved ones now posts the new files only, as the page shows; the fields of the saved files at the other indices were posted with them. No delete request goes out for those saved files: your action decides what becomes of them when it saves the form. (#B1057)
* A rule on a staged file input (`data-gina-form-upload-action`), declared under the input's name, runs again. Since 0.7.2 the input was collected without a value, so none of its rules ran, and `isRequired` on it let the form be sent with no file. With a rule, the input is now judged on the files it holds: the files it staged, a selection still staging, and the saved files an edit form shows. A required staged input with no file refuses the submit and is marked `aria-invalid`. Its own value (the browser's `C:\fakepath\` placeholder) is still never sent: the files travel through their staged fields. On a live-checked form the submit trigger follows those files: a required staged input keeps it closed until a file is chosen, and closes it again when a reset or a failed staging leaves the input with no file. A staged input without a rule is unchanged. Declare such a rule at the top level of the rule file, under the input's name or with a top-level key written as a regular expression that matches it: a rule that a `_case_` condition adds is not applied to a staged input that has no rule of its own. Known issue in 0.7.9: when a staged input has a rule of its own and a matching `_case_` condition names it too, its own value (the names of its files, or an empty string) is sent with the form's data. If fields of the input's files come before it in the form, that value lands in the files' list: under a top-level name such as `doc` it replaces the list, and the fields that came before it are lost; under a nested name such as `doc[files]` the list ends with that string. The fix ships in the next release. On the server, an input with no file sends none of the fields gina writes for its files, and `gina.plugins.Validator(rules, data, formId)` checks only the fields present in the data it is given: give it an empty string under the input's name when the body has none, or check for the files in your action. (#B1058)
* `self.sendTrailers(fields)` delivers its fields over HTTP/2. In every release from 0.4.0, which added trailer support, through 0.7.8, the render delegates sent the fields from their own `wantTrailers` listener, which runs after the one the HTTP/2 compatibility response registers when it is built; that one had already sent the response's own, empty, trailer list, so no field arrived (no trailer block, or an empty one on Bun 1.2.21). `renderJSON`, `renderStream`, `renderXML`, and `render` with swig or nunjucks (from disk or a memory loader, with or without bundle middleware) now hand each field to the compatibility response (`response.addTrailers()`), which sends them after the body. A field the HTTP/2 layer could not send is dropped when it is recorded, and the others are sent: a name that is not an HTTP token, a connection-specific name (`connection`, `upgrade`, `http2-settings`, `keep-alive`, `proxy-connection`, `transfer-encoding`, and `te` unless its value is `trailers`), a value that is neither a string nor a number, or a string value holding a character other than a tab, U+0020 to U+007E and U+0080 to U+00FF (a CR, a LF, a NUL or another control character, DEL, or a character above U+00FF). Names are sent lower-case. An answer that `throwError()` gives (a custom error page, a JSON error body) carries no trailers: it drops the fields recorded before it. A HEAD and a 204 carry none, as before: their stream ends with its headers. An action that answers on `res.stream` itself and sends trailers from its own `wantTrailers` listener still sends none: call `res.addTrailers(fields)` before `res.stream.respond(headers, { waitForTrailers: true })`. (#B1080)
* `merge()` returns when an array holds object elements and then `NaN` (#B1091). When an array inside an object the target lacks held two or more object elements followed by `NaN`, or when an array was merged with itself, `merge()` never returned: it kept pushing the `NaN` onto the source array it was walking until the heap ran out. Its primitive merge decided whether a value was already present with `indexOf`, which never finds `NaN`. A `NaN` is now present once the result holds one, and it is never topped up: `[1, NaN]` + `[NaN, 2]` gives `[1, NaN, 2]` (it gave `[1, NaN, NaN, 2]`), and merging the same source a second time is a no-op for `NaN` too. The request parsers produce no `NaN` (form and query values arrive as strings, and JSON has no `NaN`), so this takes a `NaN` the application computes. Every other value merges as before. The browser bundle carries the same fix. Pickup: a bundle restart and a re-bake.
### Security
* Over HTTP/2, a request answered while its client is still sending the body no longer leaves its stream open: once the answer has gone out whole, the server closes the stream with RST_STREAM(NO_ERROR), and the session keeps serving its other streams. This covers the 431 past `upload.maxFieldsSize` counted on a multipart request that sends no `content-length`, the 413 past `server.maxBodySize`, the 400 of a multipart body that fails to parse, and, on Bun 1.2 and 1.3, the 431 sent before the body of a request whose `content-length` is past the cap. Before, the client could keep sending into a request nobody reads: one more stream window (up to 640 KB) on Node.js and Bun 1.4, then a stall, and on Bun 1.2 and 1.3 everything it sent, which the bundle held in memory. HTTP/1.1 requests are unchanged. Pickup: a bundle restart, no re-bake (#B1071).
* On Bun, over HTTP/2, a request answered before its body is read no longer keeps what its client still sends: the body is discarded, and once the answer has gone out the server closes the stream with RST_STREAM(NO_ERROR). This covers the `/_gina/*` control endpoints and the cross-origin guard, the maintenance gate, the admin endpoints answered ahead of routing, a static file answered to a request that carries a body, and the stops of #B1071 when the client never reads its answer (a zero receive window). Before, Bun 1.2 and 1.3 held everything the client sent in memory, without bound, and Bun 1.4 held the client at the stream window. Node.js and HTTP/1.1 requests are unchanged. Pickup: a bundle restart, no re-bake (#B1076).
* Gina now requires `@rhinostone/swig` `^2.12.1` in both manifests. Up to 2.12.0, a key from the template data that names `__proto__`, `constructor` or `prototype`, or a list holding one of those names, reached the prototype chain wherever a template read a value with it: a subscript such as `{{ foo[k] }}` printed the Object constructor, a call on such a value could run text from the data as JavaScript, and a native `{% set %}` whose bracket target took the key (`{% set obj[k].x = 1 %}`) put a property on `Object.prototype` for the whole process (advisory GHSA-8mf3-p375-389g). A template is exposed when it indexes a value with a key that the request controls. 2.12.1 reads such a key as missing, and a native `set` target given one throws « Unsafe assignment to "__proto__" via bracket notation is not allowed (prototype-chain guard) » when the template runs; a template indexing with an ordinary key renders as before. The templates Gina ships use no bracket subscript, and Gina compiles a template each time it renders it and stores no compiled output, so restarting the bundle picks the fix up; output an application precompiled with swig 2.12.0 or earlier (`swig compile`, a stored `precompile()` result) keeps the old behaviour until it is recompiled with 2.12.1. Upgrading gina installs 2.12.1 or later (a project copy loaded through `swig.useProject`, or a frontend selected through `swig.package`, keeps its own version, so update it there to 2.12.1); restart the bundle. (#B1088)
* Over HTTP/2, a multipart upload that gina refuses while it parses the body now stops at the refusal: the parts it staged are removed, and once the answer has gone out the server closes the stream with RST_STREAM(NO_ERROR). This covers the 400s for too many files (`upload.maxFields`), an upload group that is not configured, an extension the group does not allow and a second file in a single-file group, the 500s of an upload directory that cannot be created, of a write error and of a multipart listener that throws, and the 400s past `upload.maxTextFieldSize` and `upload.maxTextFields`. Before, a refused file part was never read, so the parse waited on it while the client kept sending: Bun 1.2 and 1.3 held everything the client sent in memory, without bound, and Node.js and Bun 1.4 held the client at the stream window with the stream left open; when the client finished sending, the parts staged before a refused file part, or after a refused text field, stayed on disk (Node.js and Bun 1.4). A client that never reads the answer (a zero receive window) is held at the stream window on Node.js, and on Bun what it sends is discarded. HTTP/1.1 answers are unchanged: the connection closes after them, as before. Pickup: a bundle restart, no re-bake (#B1086).
* Merging an array of objects compared on their `id` (or on the key set with `merge.setKeyComparison()`) no longer takes time cubic in its length when the target already holds every id: a source array the target lacks, `merge([], items)`, an array inside an object the target lacks, and a target holding the same ids. Such a merge of 2,000 objects took about 4 to 5 seconds and blocked the event loop; it now takes a few milliseconds. With `override`, a target holding the same 40,000 ids went from about 3 seconds to under 30 ms. Results are unchanged, except that an element that refers to itself no longer throws `RangeError: Maximum call stack size exceeded` when every id is already present. `lib/merge` is in the browser bundle: restart the bundle and rebuild its static assets (`gina bundle:build`). (#B1078)
* An upload part whose `group` parameter names a member of `Object.prototype` (`__proto__`, `constructor`, `hasOwnProperty`, `toString`, …) is now answered HTTP 400 as an unconfigured upload group, like any other unknown name. Up to 0.7.8 such a part passed the configured-group check, which read the name on `upload.groups` without asking whether it was one of its own keys, and the rules then read on the group were skipped: the file was accepted whatever its extension, a single-file group accepted several, and the file was staged to the default upload directory instead of the group's. This let a client, with no account, sidestep a restricted `untagged` group or a named group's allow-list. Restart the bundle; the browser bundle does not change. (#B1089)
